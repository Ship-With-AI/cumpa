# Bring `tests/` under `tsc`

## Why

No tsconfig covers `tests/`. `tsconfig.json` includes `src/{cli,contracts,git,server}`; `tsconfig.web.json` uses `files:` and covers exactly five `src/web` modules. Everything under `tests/` — and most of `src/web` — is compiled by nothing. `tests/e2e/agent-ready-export.spec.ts` shipped with an undeclared `completedScenarios` at seven sites, survived two execution waves and a green review, and only failed at runtime with `ReferenceError`.

Two consequences this plan must both deliver: a gate that catches that class of defect, and the real bugs the gate immediately exposes.

## Config decision: two projects, mirroring the existing node/web split

**Decided: two.** The argument is resolution semantics, not convenience. Measured evidence that a single project cannot work:

Putting `src/web` into a NodeNext program (`module: NodeNext`, inherited from `tsconfig.json`) produces:

- `src/web/monaco/diff-adapter.ts` TS2835 ×4 — *"Relative import paths need explicit file extensions when `--moduleResolution` is nodenext"*. `src/web` is authored extensionless because Vite resolves it. `src/server`/`src/cli` are authored with `.js` extensions because Node resolves them. One project cannot hold both conventions without rewriting every `src/web` import into a form Vite must then be taught to handle.
- `src/web/monaco/configure.ts` TS2307 ×5 — `monaco-editor/esm/vs/.../*.worker?worker`. The `?worker` suffix is a Vite query, resolvable only via `types: ["vite/client"]`, which must not be loaded into the Node program.
- `src/web/main.ts` TS2339 ×1 — `import.meta.env`, same origin.
- `src/web/monaco/diff-adapter.ts` TS2532 ×2 — present in the NodeNext program, absent in the Bundler program.

Same file, opposite verdicts, depending purely on which resolver compiles it. That is the whole argument: the two halves of `src` are consumed by two different resolvers, so they need two programs, and each test file belongs to the program that matches the code it imports.

**Membership is by import graph, not by directory.** These ten `tests/unit` files import `../../src/web/*` and therefore belong to the *web* project:

```
agent-ready-export-state  comment-groups  draft-reconciliation  file-tree  line-mapping
markdown-preview  monaco-diff-adapter  monaco-diff-semantics  monaco-theme  workspace-state
```

Routing them correctly is what takes the raw 156 down to 124 with zero code edits.

### Bucket A — source type is incomplete; fix the type (35)

**A1 · `'diff-ready'` missing from `WorkspaceEvent` (26 diagnostics, worked example).**
`src/web/App.vue:810` dispatches `{ type: 'diff-ready', fileId }`. `src/web/model/workspace-state.ts:362` handles `case 'diff-ready':`. The union at `src/web/model/workspace-state.ts:62-...` does not declare it. The handler body therefore narrows `event` to `never`, so all seven `event.fileId` reads fail (TS2339) and the `case` itself fails (TS2678), and all 18 dispatches in `tests/unit/workspace-state.test.ts` fail (TS2322). The type is wrong; the code is right. Add the member — `Readonly<{ type: 'diff-ready'; fileId: string }>` in the union's alphabetical position — and all 26 clear with no test edit.

**A2 · `src/web/api/client.ts` (9).** `SupportStatus` is used at lines 84/86 in the `SessionClient` interface but never imported (TS2304 ×2). The returned object literal is wrapped in `Object.freeze({...})`, which drops the contextual type from the `: SessionClient` return annotation, leaving seven method parameters implicitly `any` (TS7006 at 166, 180, 193, 231, 262, 271, 307). Fix: import the type, and annotate the literal (`const client: SessionClient = {...}; return Object.freeze(client);`) so contextual typing reaches the parameters. Do not annotate parameters one by one — that re-states the interface in a second place.

### Bucket C — report; do not retype (1)

**`tests/cli/request.test.ts:293` TS2353 — `launchComparison` is not a member of `OrdinaryActionDependencies`.**
`launchComparison` exists on `RunCliDependencies` (`src/cli/run.ts:175-177`) and is consumed at `src/cli/run.ts:626-627,738`. It does **not** exist on `OrdinaryActionDependencies` (`src/cli/run.ts:182+`), which is the type of the object the test is building. The test's stub throws `'non-TTY review must use the attached launcher'` — i.e. the author believed they were guarding against the ordinary non-TTY path reaching the browser launcher. If the property is never read on that path, **that guard has never fired and never could**.

Procedure, in order:
1. Read `src/cli/run.ts` and determine whether the ordinary-action path can reach any launcher (directly, or through the injected `runCli`).
2. **If it can** — the type is incomplete, this is bucket A: declare `launchComparison` on `OrdinaryActionDependencies` and thread it to the call site. `src/cli/run.ts` is reserved to this task for exactly this branch.
3. **If it cannot** — the stub is unreachable. Do **not** add the property to make it compile, and do **not** silently delete the stub. Stop this item, leave the other 12 diagnostics in the file fixed, and report it in the SUMMARY under `Reported, not fixed`, naming the line and the reasoning. A vacuous guard is a finding, not a formatting problem.

Do not resolve this by widening `OrdinaryActionDependencies` with an index signature or an optional `unknown` member.

## Residual gap: `.vue` files stay outside `tsc` after this task

This is the honest limit of the gate. `src/web/App.vue` dispatches `'diff-ready'` at line 810 and no compiler will read that line after this change. The exact bug class that motivated the task can recur from the Vue side.

`vue-tsc@3.3.7` is already a devDependency, so closing the gap looks like a one-line addition. It is not — measured:

```
$ npx vue-tsc --noEmit -p <web test project>
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './lib/tsc' is not defined
  by "exports" in node_modules/typescript/package.json
    at Object.run (node_modules/vue-tsc/index.js:40:32)
```

`vue-tsc` shells into `typescript/lib/tsc`, which `typescript@7.0.2` no longer exports. `vue-tsc` cannot run in this repository at all today, at any config. Closing the `.vue` gap therefore requires either a `vue-tsc`release with TS7 support, or a second toolchain pinned to TypeScript 5 solely for SFC checking — both out of scope here and neither worth bundling into a config-and-triage task.

The `declare module '*.vue'` shim types SFC imports as Vue's `Component`, which makes `src/web/main.ts` checkable but does **not** check props, emits, or template expressions inside any `.vue` file.

**Recommended follow-up (separate quick task, worth doing):** re-test `vue-tsc` against the installed TypeScript on the next dependency bump and add a `typecheck:sfc` gate when it runs. Until then, `src/web/**/*.vue` is unchecked and this plan does not claim otherwise. The `.vue`-resident half of the `diff-ready` defect — the dispatch — remains uncovered; only the model-resident half is now guarded.
