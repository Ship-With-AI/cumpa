<objective>
Enable Stripe Dashboard-issued promotion codes on Cumpa's one-time USD $49.99 voluntary support
Checkout, without weakening the fulfillment invariant that today accidentally forbids every
discount: `amount_total: z.literal(4999)` in `fulfillment.ts` currently rejects any session whose
charged total differs from the full list price, so a discounted purchase would be charged and
never fulfilled.

Per D-1: pass `allow_promotion_codes: true` on the server-owned Checkout Session; no client- or
browser-supplied discount, no `discounts` array (mutually exclusive with `allow_promotion_codes`),
no new env var. Per D-2: shift the exact-amount invariant from the charged total
(`amount_total`) to the pre-discount list total (`amount_subtotal`), keeping every other
invariant (`mode`, `payment_status`, `currency`, single line item at the configured Price,
`quantity`, `customer`, `payment_intent`, metadata) exactly as strict as today, and bounding
`amount_total` to `1..4999` inclusive. Per D-3: explicitly reject `amount_total === 0` (100%-off)
because a fully discounted session has no Stripe PaymentIntent, and `payment_intent: z.string().min(1)`
plus the DB's payment-intent column are load-bearing for the fulfillment audit chain. Per D-4: no
migration — `record_checkout_session` runs at intent time before any code is entered, so its
recorded `p_amount_total: 4999` is the pre-discount list total and stays valid unchanged; the DB
CHECKs and RPC signatures are untouched. Per D-5: document the coupon/promotion-code operating
policy in the hosted-support runbook.

Purpose: let the operator run promotional discounts on the one-time support payment while keeping
Stripe as the sole settlement authority and keeping every discounted purchase fulfillable.

Output: a widened-but-still-strict `RetrievedCheckoutSchema`, a Checkout Session that surfaces the
promo-code field, matching Deno test coverage for both files, and a runbook section closing the
undocumented discount-policy gap.
</objective>
