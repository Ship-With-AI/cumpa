<objective>
Make `src/web/monaco/theme.ts` a derivation of the canonical root rather than a second hand-authored palette, and turn `tests/unit/monaco-theme.test.ts` from a mirror of two literal tables into a gate that can actually fail.

Purpose: VIS-02. Both tables can be edited consistently-but-wrongly and both pass. After this plan there is one value source and the test compares real bytes.

Output: a literal-free `theme.ts`, and a `monaco-theme.test.ts` whose mapping tables carry token names only.
</objective>

<decisions>
- **D-1TO1 — every Monaco colour is a 1:1 token reference.** No alpha arithmetic, no colour maths, no blending anywhere in `theme.ts` or in the test. The four alpha layers that used to be multipliers in the test are root tokens authored by 08-02 (D-MONACO-ALPHA). This is what makes the parity assertion non-tautological: with alpha in the root, both sides of the comparison trace to one authored byte string; with alpha in the test, the comparison degenerates into comparing a transform to itself.
- **D-PREFIX — the leading `#` asymmetry is load-bearing.** `colors` entries go through Monaco's `Color.fromHex` (`node_modules/monaco-editor/esm/vs/editor/standalone/browser/standaloneThemeService.js:73`) and require the prefix; `rules[].foreground` is consumed as a bare six-hex string (`tokenization.js:50-58,101`) and adding a prefix corrupts syntax colouring. `toMonacoHex` returns the prefixed form and the rule builder strips it.
- **D-SATISFIES — preserve the literal key types.** `src/web/monaco/theme.ts:86` uses `satisfies`, not a type annotation, and `tests/unit/monaco-theme.test.ts:139,142` index `colors` with `keyof typeof colors`. Build the `colors` object with explicit literal keys and one token lookup per value. Generating it by iterating a mapping table degrades `keyof typeof colors` to `string` and silently discards the compile-time guarantee (research Hazard 4).
- **D-NAMEMAP — the test's mapping table is a name map, not a value table.** It maps each Monaco key to a semantic token name and each token rule to a token name plus a font style. That is legitimate duplication: it gates "someone repointed a Monaco key at a different token without updating the contract". Do **not** import the mapping from `theme.ts` to remove the duplication — that would delete the only thing the assertion tests. Values must come from the canonical root on both sides; names must be independently stated.
- **D-UNPAINTED — the fully transparent sentinel stays in `theme.ts`.** Two Monaco keys are deliberately unpainted (`tests/unit/monaco-theme.test.ts:63-66`). A fully transparent value is an instruction not to paint, not a palette entry, and giving it a CSS root token would add vocabulary with no CSS consumer. It is expressed as one named constant in `theme.ts` and is the only literal the source-shape gate permits.
- **D-UNNAMED-KEYS — Monaco keys the UI-SPEC does not name reuse the nearest UI-SPEC token.** Per `08-RESEARCH.md` Open Question 1: editor whitespace and inactive selection and the two scrollbar states take the alpha-layer tokens 08-02 authored; indent guides take the collapsed-gap and default boundary roles; the overview-ruler border takes the default boundary role. Introducing a value absent from the mockup would violate "re-derived from the mockup's values". Every Monaco key whose current token was retired by 08-02 repoints to that token's successor as recorded in the 08-02 `## Token cutover ledger`.
</decisions>
