# Phase 08 — UI Design Contract

> Visual and interaction contract for Phase 08: Accessible Responsive Continuity. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Contract Boundary

Phase 08 hardens the implemented dark, side-by-side review workspace so the complete existing workflow remains readable and operable at desktop widths, narrow widths, a 320 CSS px effective viewport, 400% browser zoom, with keyboard-only input, in grayscale, and with forced colors active.

Locked decisions D-01 through D-04 in `08-CONTEXT.md` are authoritative. This contract inherits the one semantic token root, four-size/two-weight typography, 4-point spacing, non-color status language, Monaco diff layering, source-line anchor geometry, review-surface hierarchy, and exact workflow copy from Phases 05–07. Phase 08 may refine those presentation roles centrally when measured contrast or reflow fails; it MUST NOT add a parallel palette, component token root, layout state, review state, or product behavior.

Implementation MUST preserve existing information architecture, Base/Head side ownership, `renderSideBySide: true`, line mapping, paired view zones, commands, tooltips, accessible names, focus destinations, drawer state, draft persistence, revision checks, selector-drift behavior, export publication semantics, and all review mechanics. Only the side-by-side diff region may require localized horizontal scrolling. Hiding overflow is not a substitute for reflow.

### Requirement Mapping

| Requirement | Implementable visual and interaction contract |
|-------------|-----------------------------------------------|
| A11Y-01 | Normal text and control labels reach at least 4.5:1 against their actual composited background. Meaningful boundaries, icons, change bars/signs, selected rails, anchor rails, and focus indicators reach at least 3:1 against adjacent composites. Diff, selection, comment, status, hover, disabled, and focus layers are evaluated together, not as raw tokens. |
| A11Y-02 | Every operable shell, drawer, review, export, recovery, and Monaco target has a persistent two-CSS-pixel focus-visible indicator. It remains unclipped at viewport, pane, drawer, view-zone, and editor edges and remains distinct from hover, selection, lifecycle, and anchor state. |
| A11Y-03 | Forced colors retain system-color text, control boundaries, selected/current rails, literal Base/Head and `−`/`+` cues, status labels/icons/edges, comment anchors, and focus outlines. Ordinary content respects user color choices; no blanket `forced-color-adjust: none` is allowed. |
| RESP-01 | Header, toolbar, drawers, comments, notices, forms, confirmations, paths, hashes, and receipts fit and reflow at 320 CSS px and 400% zoom without document-level horizontal scrolling. A presentation-only inner diff viewport owns the unchanged 640px side-by-side canvas and its local horizontal scrollbar. |
| CONT-01 | File selection/navigation, side-by-side review, change navigation, line commenting, comment lifecycle, Summary, recovery, drift acknowledgement, gitignore consent, and Export retain their existing order, commands, focus transfers, persistence, and all-or-nothing publication semantics end to end. |

## Spacing Scale

All layout spacing remains on the inherited 4-point scale.

| Token | Value | Phase 08 usage |
|-------|-------|----------------|
| `space-xs` | 4px | Icon-to-label gap, compact metadata gap, forced-color marker clearance |
| `space-sm` | 8px | Narrow header padding, toolbar group gap, drawer viewport gutter, compact action gap |
| `space-md` | 16px | Default header/panel/form inset and section separation |
| `space-lg` | 24px | Recovery or destructive confirmation separation only |
| `space-xl` | 32px | Existing shell/drawer-safe geometry only |
| `space-2xl` | 48px | Major state separation only; not routine narrow padding |
| `space-3xl` | 64px | Existing desktop shell/header geometry only; not a narrow-screen minimum |

### Density and Target Rules

- Desktop header and section padding remains 16px inline and 8px block where Phase 07 established compact density.
- At `<= 767px`, header, toolbar, drawer, rail section, notice, confirmation, and receipt insets use 8px or 16px; no surface retains 24px+ inline padding if it causes a 320px overflow.
- Related controls use 8px gaps. Action groups wrap with an 8px row and column gap.
- File-navigation and change-navigation pairs remain intact: each `.review-toolbar__group` is `flex-wrap: nowrap`; only the outer toolbar wraps groups.
- Buttons and single-line controls remain at least 32px high. Existing icon-only toolbar and line-comment controls remain 32×32px. Existing recovery actions that are 44px high stay 44px high.
- A pointer target is at least 24×24 CSS px or has at least 24px center-to-center clearance. No responsive rule shrinks an existing target.
- Touch-target growth MUST NOT alter Monaco gutter allocation, code x-origin, line height, paired-zone geometry, or comment-anchor coordinates.

**Exceptions:** 1px separators and intraline edges, 2px focus outlines and diff change bars, 3px selection/anchor/status rails, 1.5px local SVG strokes, and 4px/6px/8px/999px radii are visual dimensions rather than spacing. There are no non-4px spacing exceptions.

## Typography

Exactly four interface sizes and two weights remain available. Phase 08 MUST NOT add a size or weight to solve reflow.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Metadata / badge / gutter sign | 12px | 400 or 600 | 16px |
| Body / controls / code / line number | 14px | 400 or 600 | 20px |
| Section heading | 16px | 600 | 24px |
| Page/state heading | 20px | 600 | 28px |

### Typography Rules

- Allowed weights are regular `400` and semibold `600` only. No `500`, `700`, synthetic bold, italic status text, condensed text, or font-size reduction at narrow widths.
- Body line-height is 20px. Heading line-heights are 24px and 28px. Browser zoom scales these values naturally; no transform-based scaling is allowed.
- Required instructions, error recovery, consent, and status text use `text-primary` or `text-secondary`, never `text-muted`.
- `BASE` and `HEAD` remain visible at 12px/16px semibold with letter spacing no greater than `0.04em`.
- Directories remain 400 and quiet; filenames remain 600 and primary. This distinction survives wrapping and forced colors through weight and position, not hue alone.
- Paths and human-readable prose use `overflow-wrap: anywhere`. Hashes, object IDs, and algorithm digests may additionally use `word-break: break-all` because they have no safe linguistic break point.
- No meaningful path, selector label, comment, notice, validation, consent, or receipt datum is available only through hover or `title`.

## Color

The implemented Phase 05 palette remains authoritative. The 60/30/10 split describes the visible workspace area across the complete screen.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0D1117` (`surface-canvas`), with `#010409` only for inset regions | Main workspace, Monaco canvas, quiet content interiors |
| Secondary (30%) | `#161B22` (`surface-panel`), with `#21262D` only for raised/interactive neutrals | Header, drawers, review sections, comment surfaces, controls |
| Accent (10% maximum) | `#2F81F7`; emphasis `#1F6FEB`; focus/selection edge `#58A6FF` | One active primary CTA, links, selected/current rails, source comment affordance/anchor, keyboard focus, copy feedback |
| Destructive | `#F85149`; emphasis fill `#B62324` | Destructive actions and error meaning only; never deletion provenance alone |

**Accent is reserved for:** the primary action in the active task region; text links; keyboard focus; selected/current file, tab, Review, and comment rails; the existing Monaco comment affordance and anchor; text-selection edge; and existing actionable copy feedback. It MUST NOT color every control, heading, endpoint, border, status badge, hover state, or forced-color surface.

### Contrast Contract

- Normal text, labels, placeholders that communicate an instruction, and control text: `>= 4.5:1` against the final composited background.
- Large text is not used to claim a relaxed threshold; the four inherited sizes are treated as normal text for acceptance.
- Meaningful control/input boundaries, checkbox/radio geometry, icons, change bars/signs, selected rails, source-anchor rails, status edges, and focus indicators: `>= 3:1` against every adjacent composite.
- Decorative separators may remain lower contrast only when no state, grouping, control boundary, or reading relationship depends on them.
- Required body/instruction copy uses `#E6EDF3` or `#B1BAC4`. `#8B949E` remains tertiary metadata only. On `#21262D`, those pairs are 12.88:1, 7.75:1, and 4.95:1 respectively.
- The existing `#30363D` and `#484F58` borders remain quiet separators, not sufficient meaningful-control boundaries. Add one canonical `control-boundary` role using `#8B949E` for fields, checkboxes, and any outlined control whose shape is necessary to identify it. This yields at least 4.95:1 against `#21262D` and 5.62:1 against `#161B22`. Do not scatter that literal through component rules.
- The opaque `#58A6FF` focus/selection edge remains the focus color; it reaches 6.85:1 against `#161B22` and remains above 3:1 across inherited neutral surfaces.
- Semantic foreground text may remain semantic only where its actual tinted-background pair reaches 4.5:1. If a browser-computed state fails, body text becomes `text-primary` while the semantic icon, heading label, and 3px edge retain the state hue. Never solve a failure by reducing font size, removing alpha-layer evidence, or inventing a component-only color.

### Required Composite Matrix

The implementation must evaluate browser-computed foregrounds and source-over backgrounds for all applicable combinations below:

1. Canvas, panel, raised, control-rest, hover, active, selected, disabled, and forced-color surfaces.
2. Normal, addition, deletion, and intraline Monaco backgrounds.
3. Focused and inactive text selection over each diff background.
4. Active line, persistent comment anchor, hover comment action, and focused Base/Head pane over those states.
5. Inline composer/card, selected rail comment, Open/Resolved, Verified/Stale/Anchor unavailable, and field validation.
6. Error, warning, information, success, pending, disabled, recovery, selector drift, export conflict, progress, failure, and receipt states.

A raw token-to-canvas calculation is insufficient. Every failure is corrected at the shared semantic role or by promoting required text to an already approved foreground.

## Responsive and Reflow Contract

### Overflow Ownership

The page, `.session-shell`, `.review-shell`, `.review-main`, grouped header, toolbar, drawers, review rail, comment zones, notices, forms, confirmations, recovery, and export receipt MUST have `scrollWidth <= clientWidth` at every accepted viewport. `overflow-x: hidden` or `clip` MUST NOT be used to conceal content that does not fit.

The current 640px constraint moves off `.review-main` and the outer `.diff-workspace`:

- `.review-main` is `width: 100%`, `min-width: 0`, and never owns horizontal page navigation.
- Add one presentation-only `.diff-workspace__viewport` with `min-width: 0`, `max-width: 100%`, and `overflow-x: auto`; it is the sole application-owned horizontal scroll region.
- Add one `.diff-workspace__canvas` inside that viewport with `position: relative` and `min-width: 640px`. It contains the Base/Head side-label row, gutter comment action, and Monaco host so their coordinate system, 50/50 pane ownership, and current `host.offsetTop` affordance calculation remain unchanged.
- The context-help paragraph stays outside the 640px canvas and wraps to the available page width.
- Monaco retains its own vertical editor scrolling. The outer diff viewport does not add a competing vertical scroll owner.
- The local scrollbar is visible and keyboard/trackpad operable. Focusing a Monaco target may scroll only this viewport enough to reveal the focused pane; it must not move the whole page horizontally.

### Header Source and Visual Order

The semantic source order for the context band is **active file identity → Base endpoint → Head endpoint**, followed by the toolbar band. Desktop CSS grid areas may visually place Base/path/Head in three columns, but narrow reading order MUST NOT be simulated only by CSS when it would leave assistive-technology reading order behind. Reordering these non-interactive endpoint blocks does not change the first actionable header destination: the existing conditional `Files` button remains part of active-file context.

| Width/effective viewport | Header and shell contract |
|--------------------------|---------------------------|
| `>= 1440px` | Existing three-region shell. Context visually uses Base / active file / Head columns. Toolbar remains one row where it fits. Static panes have no shadow. |
| `1100–1439px` | Existing files+diff shell with review overlay. Context may remain three columns while every grid child uses `min-width: 0`. Toolbar wraps only at complete group boundaries. |
| `768–1099px` | Files and review are existing edge drawers. Context becomes two rows: active file spans the first row; Base and Head remain a paired left/right second row. Toolbar is the final band and wraps whole semantic groups. `.review-main` has no 640px minimum. |
| `<= 767px` | Active file remains first. Base stacks above Head with explicit labels and left alignment. Toolbar places File navigation, Change navigation, then Review/Keyboard Help on successive rows as space requires; each pair/group remains intact. Drawers and all non-diff content fit the visual viewport. |
| `320 CSS px` and `400% zoom` | Same `<=767px` contract. No page-wide horizontal scrolling. Vertical scrolling is allowed. The inner diff viewport alone exposes the 640px side-by-side comparison through local horizontal scrolling. |

No overflow menu, unified diff, hidden action, icon-only replacement for Review/Keyboard Help, horizontal-scrolling toolbar, or narrow-only workflow is allowed.

### Header Content Wrapping

- Active path is never ellipsized in the grouped header. `.path-display`, old/new path spans, and `.path-text` allow wrapping and expose the complete safe display text inline.
- Directory text stays quieter and filenames stay stronger after wrap.
- Renamed/copied identity stays old `→` new. At `<= 767px`, old identity, arrow, and new identity may occupy three stacked lines. The arrow remains visible and the accessible `renamed/copied from … to …` label remains unchanged.
- At `768–1099px`, Base and Head keep a two-column relationship. Endpoint labels, selector names, and short OIDs wrap inside each column rather than widening the page.
- At `<= 767px`, Base precedes Head in one column. Head text becomes left aligned. Meaningful selector identity is not ellipsized; full OIDs remain available in the existing identity details.
- The decorative narrow notice `Widen the window for the clearest side-by-side review.` is removed and not replaced. Narrow review is supported, and a fixed notice must not cover a focused control.

### Drawers, Rail, Comments, Forms, and Receipts

- Files and Review retain their existing Vue-controlled drawer states, `inert`, `aria-hidden`, Escape behavior, focus destination, and return focus.
- Open drawers are viewport-bound with `box-sizing: border-box`, an 8px outer viewport gutter at 320px, and internal vertical scrolling. They begin below the visible session header and never cover its focused controls because of a stale fixed `top: 64px` assumption.
- The Files drawer is at most 288px and no wider than `calc(100vw - 16px)`. The Review drawer is at most 360px and no wider than `calc(100vw - 16px)`.
- Drawer close controls, Review close, and the currently focused destination remain visible without horizontal scroll. No focus trap or backdrop interaction is added.
- Every flex/grid child that carries user or repository text has `min-width: 0` and `max-width: 100%`.
- Comment headers, bodies, field guidance, validation, action footers, notices, and confirmations wrap. Paired Monaco zones grow through the existing measured height path; they never overlay code or gain an inner horizontal scrollbar.
- Form controls use `width: 100%` and `max-width: 100%`. Action groups wrap; at `<= 767px`, the active primary action may fill the row while neutral/destructive escape actions remain visible below it.
- Receipt/readiness/identity definition lists become one column at `<= 767px`. Relative paths, full SHA-256 hashes, revisions, timestamps, and drift observations wrap without forcing page width.
- Review Summary → Open → Resolved → Export order and Files/diff/Review information architecture remain unchanged at every width.

## Focus and Keyboard Contract

### Focus Geometry

- Default focus remains an opaque 2px `#58A6FF` outline with 2px offset, visible only under `:focus-visible`.
- Where an outer outline would be clipped by a required scroll/overflow boundary, use a component-local inset fallback of at least a 2px perimeter in the same focus role. Do not remove the default outline globally or use a color-only background change.
- A target at a viewport or drawer edge receives enough scroll padding/inset clearance for the full ring. Sticky/overlay layers may not cover it.
- The focused Base or Head Monaco pane retains the Phase 06 inner 2px pane perimeter; the caret is not the only editor-focus cue.
- Focus is always the outermost active channel. Selected file/comment/tab rails, lifecycle badges, diff fills, source anchor rails, destructive borders, and hover/pressed surfaces remain visible underneath and distinct from it.
- Programmatic focus movement occurs only at existing destinations. Responsive reflow does not create, remove, or reorder actionable destinations except through the existing drawer `inert` behavior.

### Required Focus Inventory

The persistent/unclipped contract applies to every applicable target:

- all three skip links and comparison identity disclosure/close controls;
- `Files`, `Close files`, every file-tree row, and file activation/navigation targets;
- Previous/Next file, Previous/Next change, Review, and Keyboard help;
- Monaco Base/Head editors, context controls, and the line `Add comment…` action;
- composer textarea, Add comment, discard/move confirmation, and accepted-comment heading;
- Review close, Summary disclosure/tabs/field/actions, Open/Resolved disclosures, Show/Edit/Resolve/Reopen/Delete/Copy actions;
- selector-drift checkbox and actions, revision reload/retry, gitignore choices/confirmation, export actions, receipt copy/reveal actions;
- recovery copy/reveal/confirmation/continuation controls and Keyboard Help close.

### Commands and Interaction Continuity

The following established paths remain unchanged:

- File navigation: existing file tree plus `Alt+Shift+[` and `Alt+Shift+]`.
- Change navigation: `Shift+F7` and `F7`.
- Line comment activation: pointer or `Alt/Option+Enter`; focus lands in the existing textarea.
- Monaco selection/copy, context reveal, read-only behavior, Base/Head side identity, and per-file state restoration.
- `?` opens Keyboard help; Escape follows existing help, drawer, and confirmation dismissal rules.
- Summary disclosure and Edit/Preview tab arrow-key behavior.
- Existing focus-comment command selects and reveals the exact rail comment; selected state persists separately from focus.

No hover-only action, new tab stop, focus trap, roving-tabindex rewrite, shortcut change, automatic drawer opening, or automatic source refresh is introduced.

## Forced-Colors Contract

Ordinary workspace content keeps `forced-color-adjust: auto`. Do not protect the dark palette with a blanket opt-out. The forced-color layer uses system colors and existing geometry:

| Surface/state | Forced-color mapping and durable cue |
|---------------|--------------------------------------|
| Page, panels, comments, notices, receipts | `Canvas` / `CanvasText`; 1px `ButtonBorder` where a boundary is meaningful |
| Buttons and fields | `ButtonFace`, `ButtonText`, and `ButtonBorder`; disabled text maps to `GrayText` |
| Links | `LinkText` plus existing underline/contextual link affordance |
| Keyboard focus | 2px `Highlight` outline/perimeter; inset fallback remains when an outer ring would clip |
| Selected file/tab/comment/Review | 3px `Highlight` rail or boundary plus existing selected text/ARIA/visible `Selected` label; a fill may use `Highlight`/`HighlightText` only when content remains legible |
| Base/Head diff provenance | Visible `BASE`/`HEAD`, side position, literal `−`/`+`, and continuous bars remain. Base bar is dashed and Head bar solid in `CanvasText` so provenance survives without red/green. |
| Source comment anchor | Existing 3px rail maps to `LinkText`; accepted/composer side-and-line text remains visible |
| Status notice/badge | Explicit icon, heading/label, and 3px edge remain; edge maps to `CanvasText` or `ButtonBorder`. Status meaning does not depend on preserving author hue. |
| Open/Resolved/Verified/Stale/Unavailable | Exact visible labels and distinct icon geometry remain. Resolved, stale, and unavailable are never opacity-only. |
| Monaco focused pane | Public phase-owned pane perimeter maps to `Highlight`; Monaco-owned accessibility/high-contrast behavior remains enabled |

Background tints and shadows may disappear. Therefore no selected/current, notice, comment, lifecycle, anchor, or diff meaning may depend on them. App-owned Phase 06/07 classes for change bars/signs, pane focus, source anchor, selected comment, badges, and notices must be explicitly covered by the forced-color block. Do not style private Monaco DOM to simulate high contrast.

## Workflow Continuity and Export Integrity

### Complete Review Workflow

A user must be able to perform this unchanged sequence at desktop, 320 CSS px, 400% zoom, and keyboard-only:

1. Inspect pinned comparison identities.
2. Open Files where it is a drawer and select a changed file.
3. Identify the complete active path and Base/Head endpoints.
4. Review the immutable side-by-side diff, reveal context, and navigate files/changes.
5. Add a Base or Head line comment; retain/discard unsaved text through existing confirmation paths.
6. Open Review; inspect, select, edit, resolve, reopen, or delete comments under existing eligibility rules.
7. Edit/preview/save or discard Summary changes.
8. Inspect Export readiness, resolve only the existing acknowledgement/consent gates, activate an intentional export action, and inspect/copy/reveal the resulting receipt.

Responsive presentation may wrap or scroll the diff locally, but it may not reorder these destinations, collapse them into a menu, hide them, or introduce a substitute workflow.

### Non-Actionable Comment Records

- Only open comments with verified anchors are actionable requests in export.
- Resolved comments remain historical, non-actionable records in export.
- Stale and unavailable/orphaned anchors remain non-actionable records. The applying agent is instructed not to guess or relocate them.
- Exact attention copy remains: `Stale or unavailable anchors will be exported as non-actionable records. An applying agent is instructed not to guess or relocate them.`
- These classifications do not remove existing lifecycle, delete, inspection, or copy controls inside Diff Review. Badges and comment rows do not become generic click targets.

### Intentional Export Action

Export never occurs from opening Review, saving a comment or Summary, reloading a revision, checking ignore state, appending an ignore rule, or acknowledging selector drift. Publication requires one explicit action:

- Ready: `Export review`
- Already exported: `Export review again`
- Acknowledged selector drift: `Export pinned review`
- Failed attempt recovery: `Try export again`

Support copy remains: `Creates review.json and review.md together from accepted revision {revision}. This does not apply, stage, commit, or push changes.` Here `{revision}` is the runtime accepted draft revision, not unresolved design copy.

### Stale Revision, Selector Drift, and Read-Only State

- Stale revision heading: `Review changed before export`.
- Show expected and actual revisions, state `Nothing from this export attempt was published.`, offer `Reload latest`, and explain that reload does not export automatically.
- Selector drift remains an acknowledgement gate without refresh. Heading: `Confirm export of pinned review`.
- Show pinned Base/Head identities and current moved/unavailable observations.
- Consent is unchecked by default: `I understand this export remains pinned to the original commits and records the selector drift.`
- `Export pinned review` stays disabled until checked. `Cancel export` remains available.
- A second observation invalidates consent and shows `Selected sources changed again`; acknowledgement must be repeated. Never refresh or export automatically.
- Malformed, schema-invalid, and newer-schema drafts remain visibly `Read only`; export is unavailable.
- Recovery headings remain `Local review draft needs recovery` and `This draft needs a newer Diff Review` as applicable. Draft path, problem details, `Reveal draft file`, `Copy draft path`, and the existing backup-before-replace contract remain visible and operable at narrow widths.

### Gitignore Consent

`.gitignore` mutation is never automatic and never a side effect of export.

- Export remains available when `.diff-review/` is not ignored.
- First choices: `Add to .gitignore` and `Keep .gitignore unchanged`.
- `Add to .gitignore` opens confirmation only.
- Confirmation states: `Diff Review will append exactly /.diff-review/ to the repository-root .gitignore. Existing bytes and rules will be preserved.`
- Final actions: `Keep .gitignore unchanged` and `Append ignore rule`.
- Busy copy: `Appending one ignore rule…`; retry: `Try append again`.
- Mutation is append-only and preserves every existing byte/rule. Ambiguous or failed outcomes never claim success, replacement, or rollback and do not block independent export.

### Progress, Failure, and Receipt

Export progress uses one decorative spinner, one status owner, and exact stages:

- `Preparing accepted revision {revision}…`
- `Validating export pair…`
- `Publishing export pair…`

Progress states that `review.json` and `review.md` become available only after both pass validation and publication checks. It never says one file succeeded and never displays a partial receipt.

Failure heading is `Export was not published` or `Export needs recovery`. State that no success receipt is available; offer `Try export again` and `Return to review`. A prior receipt may remain only in a dashed, subordinate `Previous confirmed export` block with: `This last confirmed pair remains available; the later export attempt was not published.` It is not success for the failed attempt.

A current success receipt appears only after atomic validation/publication of both files and includes:

- `Review export complete`;
- `Both files were published together from accepted revision {revision}.`;
- accepted draft revision;
- export timestamp in a semantic `<time datetime>`;
- drift value and acknowledged pinned/current identities when applicable;
- repository-relative path for each file, never an absolute path;
- algorithm and full SHA-256 hash for each file;
- byte count for each file;
- `Copy all receipt details` and `Reveal export directory`;
- `Copy acknowledged identities` when drift was acknowledged.

Reveal failure remains: `Could not reveal the export directory. Copy the relative path and open it from the repository root.` Copy/reveal results use the existing single status owner and existing focus behavior.

| Export empty state | `No review requests yet` / `You can still export the accepted empty review record, or add a summary or comment first.` |
| Empty comparison | `No changes in this pinned comparison` / `The merge base and head resolve to identical trees. Open Comparison identities to review the pinned commits, then press Ctrl+C in the terminal when you are finished.` |
| Diff error | `Diff couldn’t be loaded` / `The pinned file content is unavailable. Try again, or relaunch Diff Review if the session ended.` / `Try loading diff again` |
| Review operation error | `Review change failed`; state that the accepted local draft is unchanged or unsaved text remains, then direct the user to check Diff Review is running |
| Export revision error | `Review changed before export` / `Nothing from this export attempt was published.` / `Reload latest` |
| Export failure | `Export was not published` or `Export needs recovery`; never claim partial success |
| Export success | `Review export complete` / `Both files were published together from accepted revision {revision}.` |
| Comment discard | `Discard this comment draft? Your text hasn’t been saved.` Actions: `Keep writing`, `Discard draft` |
| Comment edit discard | `Discard comment edits?` / `Your saved comment will stay unchanged.` Actions: `Keep editing`, `Discard edits` |
| Delete comment | `Delete comment?` / `This permanently removes the comment from this local draft. Diff Review has no undo history.` Actions: `Keep comment`, `Delete comment` |
| Summary discard | `Discard unsaved summary changes?` / `Your saved summary will stay unchanged.` Actions: `Keep editing`, `Discard changes` |
| Recovery destructive confirmation | `Start a new draft?`; retain byte-for-byte backup, no-replacement-on-failure, empty-new-draft, and no-undo text. Actions: `Keep existing draft`, `Back up and start new` |
| Gitignore confirmation | `Add export directory to .gitignore?` / `Diff Review will append exactly /.diff-review/ to the repository-root .gitignore. Existing bytes and rules will be preserved.` |
| Prohibited narrow copy | Remove `Widen the window for the clearest side-by-side review.` and add no replacement blocker or apology |

Do not add GitHub-specific terms such as approval, request changes, viewed, suggestion, pending review, conversation reply, PR number, merge, or submit review.

## Accessibility and Responsive Acceptance Matrix

Targeted real-browser proof is required during implementation; source inspection alone is insufficient.

### Reflow and Long Content

1. Exercise viewport widths `1440`, `1280`, `1100`, `1099`, `768`, `767`, `640`, and `320` CSS px with normal and renamed/copied paths, long selector labels, full hashes, long comments, validation, selector drift, gitignore confirmation, failure, and success receipt.
2. Exercise 400% browser zoom from a 1280px-wide starting viewport and verify the effective 320 CSS px contract; do not treat a transform or screenshot scale as zoom.
3. At every step require document `scrollWidth <= clientWidth`. Require the inner diff viewport to have `scrollWidth > clientWidth` at 320px while all non-diff surfaces fit.
4. Verify header visual/reading order, paired then stacked endpoints, complete path wrapping, old → new stacking, and semantic toolbar-group wrapping.
5. Open each drawer at 320px and 400% zoom. Verify viewport gutter, internal vertical scroll, no horizontal scroll, close action visibility, `inert` state, Escape, focus entry, and return focus.
6. Verify comments and Monaco paired zones grow without horizontal scrolling, clipping, code overlap, or changed code/gutter geometry.

### Contrast, Grayscale, and Forced Colors

7. Collect browser-computed foreground/background composites for the required matrix and require 4.5:1 normal text and 3:1 meaningful non-text indicators without rounding a failing value upward.
8. Verify every resting field/checkbox and any visually outlined control required for recognition uses the canonical high-contrast control boundary, not the quiet separator border.
9. Repeat representative unchanged/addition/deletion/selection/active/anchor/focus, review status, and export/recovery states in grayscale. Labels, signs, edges, icons, and structure remain sufficient without naming a color.
10. Emulate forced colors in Chromium for the complete representative matrix and, where available, repeat on a real Windows High Contrast configuration. Emulation is required evidence but does not replace the real-system pass when that environment is available.
11. In forced colors, verify literal Base/Head and `−`/`+` cues, dashed Base vs solid Head change bars, source anchor, selected rail, visible labels, control borders, and focus indicators remain. Assert no ordinary workspace root opts out with `forced-color-adjust: none`.

### Focus and Workflow

12. Traverse every target in the focus inventory at desktop, 320px, and 400% zoom. At each stop verify a full persistent ring/perimeter is visible and unobscured; focus and selected/lifecycle/anchor/destructive states remain distinct.
13. Exercise the complete keyboard workflow: skip links, Files, file selection/navigation, change navigation, both Monaco panes, context reveal, line comment activation/save/discard, Review, selected comment, edit/resolve/reopen/delete, Summary tabs/save/discard, drift consent, gitignore consent, export, receipt copy/reveal, and drawer/help dismissal.
14. Preserve exact commands, ARIA relationships, focus transfers, and live/alert ownership. No duplicate progress announcement or decorative marker enters the tab order.
15. With reduced motion, spinner rotation and drawer transitions stop while progressive words, structure, focus, and all operations remain available.

### Export and Recovery Integrity

16. Prove export only follows `Export review`, `Export review again`, `Export pinned review`, or `Try export again` and never follows reload, acknowledgement, ignore append, comment save, or Summary save.
17. Prove selector drift can be acknowledged without refreshing, a second drift invalidates consent, and stale-revision conflict publishes nothing.
18. Prove malformed/schema-invalid/newer-schema drafts remain read only and cannot export; recovery never replaces existing bytes before verified backup.
19. Prove `.gitignore` changes only after explicit two-step consent, appends exactly one rule, preserves existing bytes, and remains independent from export.
20. Prove progress/failure never claims partial publication. Confirm current receipt relative paths, full hashes, accepted revision, timestamp, drift, byte counts, and copy/reveal actions.
21. Preserve resolved, stale, and unavailable/orphaned records as non-actionable export records and preserve the explicit no-guess/no-relocation instruction.
