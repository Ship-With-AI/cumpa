# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## UI Impact Boundary

Phase 13 adds one source-specific presentation to the existing authenticated Vue review workspace: an agent-submitted exact patch that has already passed repository preimage and implemented postimage validation. The browser is a read-only viewer of the frozen patch bytes and an editor only for existing review feedback. It is not a patch editor, patch applier, request builder, validation wizard, or worktree repair tool.

A valid patch session MUST open directly in the established file-tree, Monaco diff, comments, summary, persistence, and ordinary export workspace. Only the source identity, preimage/postimage terminology, exact-patch empty/error/drift states, and truthful file metadata differ from existing interactive and range sessions. Interactive comparison and agent range presentation remain unchanged.

Malformed patches, patches with an ungrounded preimage, postimage mismatches, unsafe or corrupt paths, and validation failures MUST fail in the invoking terminal before browser launch. The browser MUST NOT add a screen for repairing, editing, acknowledging, or force-accepting a rejected patch.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Metadata / status | 12px | 600 | 16px |
| Body / code values | 14px | 400 | 20px |

Weights are limited to regular 400 and semibold 600. Body line-height is 20px; section-heading line-height is 24px; page-heading line-height is 28px. Full patch digests, object IDs, modes, and exact path values use the existing monospace family at 14px/20px. Do not use the existing display-size token in the review workspace and do not introduce a fifth size.

| Role | Value | Usage |
|------|-------|-------|

| Secondary (30%) | `#161B22` | Session header, file inventory, review rail, patch-scope panel, cards, and navigation surfaces |

Accent is reserved for the selected file indicator, active disclosure state, links, and `View patch scope`. It MUST NOT color the patch digest, every button, ordinary body text, file-status badges, preimage/postimage labels, or all metadata values. Status must always include text or an accessible label; color is never the sole signal.

## Visual Hierarchy

1. The session header identifies the source as an exact patch before any file-specific detail. Its heading is `Compare: exact patch · {first 12 digest characters}`.
2. A neutral existing pin-cue treatment adjacent to the heading reads `Frozen verified patch`. This cue is not a success toast and does not imply the worktree can no longer drift.
3. The header disclosure reads `View patch scope`. Opening it is informational and MUST NOT alter the selected file, scroll position, comments, draft revision, or snapshot.
4. The changed-files tree remains the primary navigation surface. It contains exactly the server-authoritative patch inventory and no repository changes outside the submitted patch.
5. The file context header uses patch semantics: eyebrow `Exact patch`, left endpoint `Preimage`, and right endpoint `Postimage`. It MUST NOT present one pair of base/head commit IDs as though an exact patch were a commit range.
6. Monaco side labels use `PREIMAGE` with `− REMOVED` and `POSTIMAGE` with `+ ADDED`. Added files show an absent preimage; deleted files show an absent postimage through the existing empty-side diff behavior.
7. The existing review rail, comment composers, summary, keyboard help, and export section retain their current hierarchy and behavior.

Do not add a landing page, agent avatar, patch-status dashboard, digest banner above every file, request JSON preview, validation checklist, or extra confirmation between browser launch and the workspace.

## Interaction Contract

### Valid exact-patch launch

- After terminal-side validation succeeds, the browser opens directly into the authenticated existing review workspace. No browser source picker, patch preview, or approval gate appears.
- The file tree contains only the accepted patch inventory. The first text-reviewable file follows established selection behavior; unsupported entries remain selectable for metadata inspection.
- File content, paths, statuses, modes, availability, line counts, patch digest, draft identity, and feedback provenance all come from the same frozen patch scope.
- Opening or closing `View patch scope` does not revalidate, reapply, parse, refresh, or mutate the patch.
- Copying the patch digest is the only new patch-scope action. It has no repository or draft side effect.

### Truthful patch file semantics

- Added, modified, deleted, renamed, copied, mode-only, symlink, binary, submodule, non-UTF-8, oversized, and other unsupported entries stay visible in the same inventory. An unsupported inline diff MUST NOT remove the file from the scope.
- Renames and copies show both Git-derived old and new paths with similarity when available. Paths use existing exact-path DTOs and control-safe display; invalid display bytes are never decoded optimistically.
- Mode-only entries show `Mode changed`, both modes in File Details, and `Line counts unavailable` when no meaningful text count exists.
- Binary, symlink, submodule, non-UTF-8, oversized, and mode/type entries use existing metadata notices and reasons. No fake text preview, patch-source view, or download fallback is introduced.
- The browser does not independently parse unified diff text, infer status, calculate paths, or compare the live worktree.

### Frozen snapshot and repository drift

- Once accepted, all reviewed preimage and postimage bytes are served from the owned frozen snapshot until review completion or explicit session failure. Navigation, retry, reload, and opening File Details MUST address that snapshot only.
- A later repository or worktree change MUST NOT alter the file tree, active diff, modes, paths, digest, comments, or summary already shown.
- When the server reports post-launch implementation drift, keep the frozen workspace readable and display the persistent error notice below. Do not silently continue as current, dismiss the notice, acknowledge drift, or offer `Refresh`, `Use current files`, `Revalidate`, `Apply patch`, or `Continue anyway`.
- A browser reload may reconnect to the same owned snapshot. If that snapshot no longer exists, is corrupt, is incomplete, or is read-only in a way that prevents its authenticated read, show the blocking frozen-snapshot failure; never rebuild from current repository content.
- The only recovery from implementation drift or lost snapshot is to relaunch Compare with an exact already-applied patch that matches current repository/worktree content.

### Review behavior retained

- Existing file navigation, Monaco context controls, keyboard commands, inline comment composition, comment editing/deletion/resolution, overall summary, draft persistence, and ordinary export remain unchanged.
- Source bytes are read-only; review feedback remains editable through existing controls.
- Phase 13 adds no `Finish review` action, attached-process status, success receipt, publish claim, or result-delivery state. Those belong to Phase 14.

### State matrix

| State | Visual and interaction result |
|-------|-------------------------------|
| Valid patch with text files | Existing workspace; first text-reviewable file selected; exact patch heading, patch scope, and preimage/postimage labels visible. |
| Valid patch with only unsupported or metadata-only entries | File tree remains populated; first entry is selectable; File Details explains availability; no fabricated Monaco diff. |
| Defensive accepted patch with zero inventory entries | Existing empty-state geometry with exact-patch copy below; `View patch scope` remains available. |
| Added file | Status `Added`; preimage shown as absent; postimage is the frozen implemented content. |
| Deleted file | Status `Deleted`; preimage is repository-grounded frozen content; postimage shown as absent. |
| Rename or copy | Git-derived old and new paths and similarity remain visible; diff uses the frozen corresponding sides. |
| Mode-only, symlink, binary, submodule, non-UTF-8, oversized, or unsupported file | Inventory and metadata remain visible; inline content follows existing availability behavior. |
| Worktree/repository drifts after acceptance | Frozen workspace remains unchanged and readable; persistent non-dismissible error notice appears; no refresh or acknowledgement action. |
| Frozen snapshot file read fails transiently | Existing diff error geometry with `Frozen patch file unavailable` and a retry that reads only the same snapshot. |
| Frozen snapshot is lost, corrupt, incomplete, or cannot be authenticated | Blocking `Frozen patch unavailable` state; no live-repository fallback. |
| Patch malformed, preimage ungrounded, postimage mismatched, unsafe, corrupt, or otherwise rejected | No browser UI. CLI exits nonzero with actionable diagnostics before browser launch. |

## Responsive Behavior

| Width | Contract |
|-------|----------|
| 1440px and above | Preserve established three-column workspace: 320px files, flexible diff, 360px review rail. `Patch scope` is a right-aligned overlay up to 520px wide with internal vertical scrolling; it never narrows Monaco. |
| 1100–1439px | Preserve 256px file column and overlay review rail. Patch scope remains an overlay and never displaces the diff. |
| 768–1099px | Preserve established file and comments drawers. Patch scope is at most 480px wide with at least 16px to viewport edges. Header facts may wrap without truncating the 12-character digest. |
| 320–767px | Patch scope becomes the established full-width modal sheet below the 96px minimum header, one column with square viewport edges. Digest and worktree path wrap anywhere without horizontal page scrolling. Rows stack label, value, then copy control; controls meet the 44px target size. |

At every width, the full digest and exact paths in Patch scope and File Details MUST NOT be ellipsized. The 12-character abbreviation is allowed only in the session header. File status, path, counts, and availability may reflow using existing file-row behavior, but no file may disappear solely because of viewport width.

## Accessibility Behavior

- `View patch scope` is a native button with `aria-expanded` and `aria-controls` bound to the panel.
- On desktop the panel is a labelled `region`. On viewports below 768px it is a modal `dialog`; focus moves to its close control, Tab is contained while open, Escape closes it, and focus returns to the disclosure.
- `Patch scope` is the accessible name. The full digest is a `<code>` value; the copy control is named `Copy full patch digest`. Copied feedback is announced politely without moving focus.
- The header heading includes “exact patch”; screen-reader users do not have to infer the source mode from a visual badge.
- Patch Monaco has an accessible label equivalent to `{path}: preimage and postimage side-by-side diff`. Visible side labels and comment affordance names use `preimage` and `postimage`, even if internal anchor sides remain `base` and `head` for compatibility.
- File status badges retain full hidden labels (`Added`, `Modified`, `Deleted`, `Renamed`, `Copied`, `Mode changed`). Availability markers include text. Old/new path order is represented in DOM order, not only by an arrow.
- The changed-files tree retains roving focus, arrow-key navigation, visible selection, and the `Changed files` accessible label. Unsupported files remain keyboard-selectable for metadata inspection.
- The drift notice uses one stable `role="alert"` announcement when drift first appears. Subsequent renders MUST NOT repeatedly announce unchanged drift. The notice remains in reading order before the review shell and cannot be dismissed.
- Loading uses polite live status. A transient frozen-file failure uses one alert and preserves retry focus. The blocking snapshot failure moves focus to its heading once and does not create an alert loop.
- Existing 2px `#58A6FF` focus ring, reduced-motion behavior, forced-colors borders, semantic text labels, and 44px narrow-screen targets remain in force.
- Frozen source bytes do not disable feedback controls. Existing resolved comments remain distinguishable; stale or orphaned anchors retain their established non-actionable treatment rather than being rebound to a current worktree line.

## Non-Goals

- No browser patch input, paste area, file upload, drag-and-drop, request editor, request JSON preview, or protocol-version chooser.
- No browser repair or override for invalid syntax, ungrounded preimages, postimage mismatch, unsafe paths, or rejected patches.
- No patch application, reverse application, staging, committing, checkout, reset, object-store write, worktree write, or index write action.
- No client-side unified-diff parser, path decoder, Git status inference, hash recomputation, live-worktree diff, or repository polling as the source of truth.
- No current-content refresh, drift acknowledgement, “continue anyway,” snapshot reconstruction, or fallback from frozen bytes to moving repository/worktree bytes.
- No second review workspace, patch dashboard, provenance page, validation wizard, or per-file proof table beyond established metadata and the patch-scope disclosure.
- No change to interactive source selection, agent revision-range scope, authenticated routing, ordinary comment/summary behavior, draft recovery, or ordinary export behavior.
- No new export action, gitignore-consent flow, receipt, selector-drift acknowledgement, or publication claim.
- No `Finish review`, attached lifecycle, canonical stdout result, completion receipt, or success state; those belong to Phase 14.
- No multi-request switcher, collision-management UI, remote review, or multi-reviewer behavior; request isolation is completed in Phase 15.
- No detached or prospective patch whose postimage does not match current implemented content; `PATCH-06` is explicitly future scope.
- No new component framework, icon package, font, theme, animation system, or visual redesign.
