# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## UI Impact Boundary

Phase 14 adds an attached completion lifecycle to agent-submitted range and exact-patch reviews. Both input modes MUST continue to open directly in Cumpa's existing authenticated Vue review workspace. File navigation, Monaco side-by-side diffs, line comments, open/resolved comment organization, summary editing, repository-local draft persistence and recovery, keyboard help, identity disclosures, file metadata, selector-drift presentation, and ordinary export remain visually and functionally unchanged.

Only an agent-submitted attached session shows completion UI. Interactive TTY-launched comparisons MUST NOT show an attached status or `Finish review` action. Phase 14 does not create a second review workspace, a request-status page, or a terminal monitor.

`Finish review` is the sole browser action that can request successful completion. Exporting, closing the review rail, closing the tab or browser, reloading, navigating, losing the browser connection, or completing an ordinary export MUST NOT finish the attached review and MUST NOT show completion success.

Every status includes text and an accessible name; color is never the sole signal.

## Visual Hierarchy

1. Preserve the existing session header, source identity, pin cue, and identity disclosure as the first level of context.
2. In attached sessions only, add one compact neutral header fact: `Agent attached · waiting for Finish review`. It sits with existing header facts and never becomes a page banner, modal, toast, or obstruction over Monaco.
3. Preserve the changed-files tree/drawer and Monaco diff as the primary review surface. Completion UI MUST NOT narrow, replace, dim, or cover the diff while the session is waiting.
4. Preserve the review rail order through Summary, Open comments, Resolved comments, and Export. Append one `Finish attached review` section after Export so ordinary export and attached completion remain visibly separate operations.
5. The completion section uses the existing panel border, secondary surface, `ReviewStateBadge`, `.ui-button`, spinner, and `InlineNotice` patterns. It contains one enabled primary CTA at a time. Do not add a sticky footer, full-screen confirmation, celebration state, or second accent treatment.
6. Completion failures remain inline in the completion section. The existing diff and review content stay readable so the developer can recover. Successful completion replaces the completion controls with a compact success state while leaving the reviewed content readable until the attached server closes.

## Interaction Contract

### Attached waiting state

- Both agent range and exact-patch requests enter the same existing review workspace and immediately show the neutral attached fact and completion section.
- The default completion badge reads `Waiting`. Adjacent body copy states that the requesting agent is waiting and that only `Finish review` returns feedback.
- Review navigation, Monaco, comment and summary mutations, persistence, draft recovery, and ordinary export work normally while waiting.
- Opening or closing files, review, identity, export, or keyboard-help panels has no lifecycle side effect.
- An attached session with zero comments and an empty summary is still finishable. The UI truthfully identifies that an empty accepted review will be returned; it does not invent required feedback.

### Readiness before finishing

- `Finish review` is enabled only when the browser has an accepted draft revision, no visible persistence conflict, no known corrupt/read-only draft failure, and no unsaved summary or comment buffer.
- If a draft mutation is already pending, show `Saving review changes…` and temporarily disable the CTA. Server-side completion MUST still settle any mutation that races with the click; browser readiness is not the source of truth.
- Unsaved text shows a warning and `Review unsaved text`. The developer must save or discard it before finishing so the one-shot result never silently excludes typed feedback.
- A known persistence conflict keeps `Finish review` disabled and reuses `Reload latest`. Reloading adopts the latest accepted revision but does not finish automatically.
- A known exact-patch drift or unavailable/corrupt/read-only review keeps `Finish review` disabled. The UI gives the relevant scope/reload/relaunch recovery; there is no `Continue anyway` or force-finish action.

### Explicit finish

- A single activation of `Finish review` starts completion. No second confirmation modal is added because the action label and adjacent consequence copy are explicit; duplicate clicks are suppressed immediately.
- Replace the button label with `Finishing review…`, include the existing spinner, set `aria-busy="true"`, and disable all review mutation and export actions until the attempt settles. File/diff navigation remains available for reference.
- Status copy reads `Validating accepted revision {revision} and its recorded anchors…`. The browser does not claim that feedback is returned during validation, serialization, or transport.
- The finish request validates the exact attached range/pathspec or patch identity and accepted summary/comments/anchors. A prior ordinary export, selector-drift acknowledgement, or gitignore consent is not completion consent and cannot bypass finish validation.
- The UI enters success only after the server confirms the one-shot canonical completion. Success must correspond to one validated result; no partial, provisional, queued, or “almost complete” success state is permitted.

### Successful completion

- Replace the CTA and waiting copy with a success notice headed `Review finished`.
- Body copy is exactly `The accepted review was returned to the requesting agent from revision {revision}. You can close this tab.`
- Change the header fact to `Agent review finished`. Disable comment, summary, export, and finish mutations because the one-shot returned result is immutable. The file tree, diff, comments, summary, and existing receipts remain readable until the session closes.
- Do not offer `Finish again`, `Send again`, `Undo finish`, or an editable success receipt.

### Failed or stale completion

- Any validation, persistence, serialization, or delivery failure leaves the attached review unfinished. Never show the success color, success icon, `Review finished`, or returned-feedback language.
- A revision conflict shows `Review changed before finish`, both expected and actual revisions, the statement `No feedback was returned.`, and `Reload latest`. After reload, the developer reviews the accepted state and must explicitly choose `Finish review` again.
- For a stale or unavailable anchor, render only the Copywriting Contract's exact `Review can’t be finished` heading, stale-feedback body, and `Review stale feedback` action. The action opens the relevant comment group and focuses the first affected comment heading only; it MUST NOT change a recorded anchor, focus a Monaco line, relocate or rebind an anchor, or reactivate a stale/orphaned comment. The developer may delete and recreate affected feedback against a verified line or relaunch the review, then explicitly finish again.
- For stale submitted range scope, render only the exact `Reviewed content changed` heading, range-scope body, and `View review scope` action. For stale submitted exact-patch content, render only that heading, the exact-patch body, and `View patch scope`. Both recoveries inspect the recorded source scope and require relaunching the agent request against valid content; neither acknowledges drift nor refreshes reviewed bytes.
- A corrupt, incomplete, or read-only accepted draft shows `Review draft can’t be validated`, states that no feedback was returned, and provides `Reload review`. If reload cannot recover the authenticated draft, copy instructs the developer to relaunch Cumpa.
- A retryable generic failure shows `Review was not finished`, the exact statement `No feedback was returned. Check that Cumpa is still running, then try Finish review again.`, and the action `Try Finish review again` only after the current attempt has definitively failed.

### Reload, close, export, and disconnect are not success

- Ordinary export retains its existing states and receipts. After a confirmed export in an attached session, add support copy: `Export complete. This attached review is still unfinished. Choose Finish review when you are ready.` Export success remains export success only.
- Closing the review rail or tab/browser produces no lifecycle request and no completion toast. The persistent waiting copy already explains the consequence; do not add a new unload confirmation solely for attachment.
- Reloading while waiting reconnects to the same server-authoritative attached state and returns to `Agent attached · waiting for Finish review`. Reload MUST NOT replay the finish request or infer completion from an earlier click.
- If connection is lost while waiting, show `Attached review disconnected` and `The browser lost its connection to Cumpa. This review is still unfinished. Reload this page while Cumpa is running, then choose Finish review.` Action: `Reload page`.
- If connection is lost after Finish was sent but before confirmation, show `Completion status unavailable` and `Cumpa disconnected before this tab received confirmation. This tab does not claim the review was finished. Check the invoking terminal. If Cumpa is still running, reload to reconnect.` Action: `Reload page`. Do not automatically retry an outcome whose status is ambiguous.

## State Matrix

| State | Visible contract | Allowed recovery / action | Completion result |
|-------|------------------|---------------------------|-------------------|
| Attached, accepted draft ready | Neutral `Waiting` badge, consequence copy, enabled `Finish review` | Continue reviewing, export, or Finish | Unfinished until CTA activation succeeds |
| No accepted feedback | `No feedback added` copy; enabled `Finish review` | Add feedback or finish empty review | Unfinished |
| Unsaved text | Warning `Unsaved text must be reviewed`; Finish disabled | `Review unsaved text`, then save or discard | Unfinished |
| Draft mutation pending | `Saving review changes…`; Finish disabled | Wait for settlement | Unfinished |
| Revision conflict | `Review changed before finish`; Finish disabled | `Reload latest` | Unfinished |
| Finishing | Spinner, `Finishing review…`, validation status; mutations/export disabled | Wait; navigation remains readable | No success claim |
| Validated canonical completion confirmed | `Review finished` success state | Close tab; content remains read-only | Exactly one success |
| Stale/unavailable feedback anchor | Error notice; affected comments stay stale/orphaned and non-relocatable | `Review stale feedback`; delete/recreate or relaunch | Unfinished; no feedback returned |
| Attached scope or exact-patch content invalid | `Reviewed content changed` | View scope, then relaunch | Unfinished; no feedback returned |
| Corrupt/incomplete/read-only draft | `Review draft can’t be validated` | `Reload review`, then relaunch if needed | Unfinished; no feedback returned |
| Generic definitive finish failure | `Review was not finished` | `Try Finish review again` | Unfinished; no feedback returned |
| Ordinary export succeeds | Existing export receipt plus unfinished support copy | Continue review or explicitly Finish | Unfinished |
| Review rail closes | Existing workspace with rail closed | Reopen Review | Unfinished |
| Browser reloads | Rehydrated attached server state | Continue review; explicit Finish still required | Unfinished unless server reports an already confirmed completion |
| Browser closes | No browser completion state | Reopen while process remains attached | Unfinished |
| Disconnect while waiting | `Attached review disconnected` | `Reload page` | Unfinished |
| Disconnect during ambiguous finish | `Completion status unavailable` | Check invoking terminal; reload if server remains | No browser success claim and no automatic retry |
| Interactive TTY review | Existing UI only; no attached fact or Finish section | Existing review/export actions | Not an attached lifecycle |

## Accessibility Behavior

- `Finish attached review` is a labelled `<section>` in the review rail. `Finish review` is a native button and is the only completion control with primary emphasis.
- The neutral attached fact contains visible text; “waiting” is not communicated by color or spinner alone.
- Disabled Finish states always have adjacent visible explanatory copy. Do not rely on a disabled-button tooltip.
- On activation, keep focus on the button as it becomes `Finishing review…`; set `aria-busy="true"` and expose the validation message through one polite live-status update.
- On confirmed success, move focus to the `Review finished` heading with `tabindex="-1"` and announce it once with polite status semantics. Do not use an alert for success.
- On conflict, stale validation, corrupt/read-only draft, generic failure, or disconnect, use the existing `InlineNotice` error/warning geometry with `role="alert"`. Move focus to the notice heading after the state renders. Do not repeatedly announce an unchanged failure.
- `Review stale feedback` opens the correct Open or Resolved group and focuses the first affected comment heading only. It MUST NOT change a recorded anchor, focus a Monaco line for a stale/unavailable anchor, relocate or rebind an anchor, or reactivate a stale/orphaned comment.
- Existing resolved, stale, and orphaned badges, exact recorded-anchor details, disabled Show/Edit controls, Inspect recorded file, and Copy anchor details behavior remain intact and keyboard reachable.
- Reload and retry controls are native buttons. Focus returns to the completion heading or relevant recovery target after state changes.
- Existing skip links, file-tree roving focus, Monaco accessible labels, visible 2px `#58A6FF` focus ring, reduced-motion zero-duration behavior, forced-colors support, semantic icons with text, and narrow-screen 44px targets remain in force.
- Finishing locks mutations through actual `disabled`/`aria-disabled` states, not pointer-events alone. Read-only navigation retains normal focus order.
- Success, error, warning, pending, and export state must remain distinguishable in forced-colors mode through text and borders, not background color alone.

## Non-Goals

- No second browser workspace, attached-session dashboard, request queue, terminal output viewer, agent avatar, or chat UI.
- No attached completion UI in existing interactive TTY review sessions.
- No automatic completion on export, review-rail close, browser close, reload, navigation, idle timeout, disconnect, last-comment resolution, summary save, or zero-feedback state.
- No modal confirmation, celebratory animation, completion sound, toast-only success, or sticky Finish bar.
- No browser generation, preview, download, copy, or reveal action for canonical stdout JSON.
- No retry after an ambiguous disconnect until server-authoritative state is recovered; no client-side exactly-once inference.
- No refresh-to-current, selector reinterpretation, current-worktree fallback, stale-anchor relocation, orphan reactivation, `Continue anyway`, or force-finish override.
- No change to ordinary export mechanics: `Export review` remains a separate, explicitly consented action; selector-drift acknowledgement never refreshes reviewed bytes; gitignore updates remain optional, separately consented, append-only, and never automatic; pair-publication status remains truthful and never presents partial publication as success; receipts retain canonical comparison identity, repository-relative JSON and Markdown paths, hashes, accepted revision, time, drift status, and copy/reveal actions. Phase 14 performs no user-visible source-control mutation and adds no apply, stage, commit, push, ref-switch, or history-rewrite action.
- No new destructive action. Existing comment deletion and its confirmation remain unchanged.
- No change to file inventory, Monaco rendering, line mapping, comment semantics, summary semantics, draft format, recovery UI, identity panel terminology, or exact-patch frozen-content rules.
- No multi-request switching, identity-collision management, remote reviewer, or concurrent reviewer UI; isolation is Phase 15.
- No shadcn initialization, third-party registry, new component library, icon dependency, font, or parallel design tokens.
