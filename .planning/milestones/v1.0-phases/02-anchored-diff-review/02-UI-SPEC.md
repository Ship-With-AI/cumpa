# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Contract Status and Sources

This contract is prescriptive for Phase 2 planning. It implements the locked decisions in `02-CONTEXT.md` and the Phase 2 requirements in `REQUIREMENTS.md`; it does not reopen them.

**Implementation baseline:** Phase 1 is unexecuted as of 2026-07-11. No product source, package manifest, components, or design tokens exist. Phase 1 plans are tentative handoff information, not source code or an implemented design system. A Phase 2 plan must first inspect the actual Phase 1 output and reconcile component names and seams without changing this user-visible contract or creating a parallel identity header, file tree, path representation, security boundary, or API vocabulary.

**Aesthetic direction:** a warm, compact code-review workbench: editorial rather than dashboard-like, with the code diff as the dominant plane, restrained chrome, crisp rules, square-to-soft geometry, and color used for selection, focus, and code semantics rather than decoration. No gradients, glass effects, glow, nested cards, or decorative metric tiles.

## Design System

| Property | Value |
|----------|-------|
| Tool | Minimal local Vue primitives; no third-party component system |
| Preset | Not applicable |
| Component library | None |
| Icon library | None; use a single local set of simple 16px inline SVG paths, with visible text or an accessible name and tooltip for every icon-only action |
| Font | UI: `"Avenir Next", Avenir, "Segoe UI", sans-serif`; code and immutable IDs: Monaco's configured platform monospace stack |
| Theme | One light theme in Phase 2; user-selectable themes are v2 scope |

### Foundation primitives to establish before Phase 2 composition

Because no coherent implemented system exists yet, implementation must define these minimal primitives/tokens first, then compose the workspace from them:

- `UiButton`: `primary`, `secondary`, `quiet`, `destructive`; 32px compact and 36px default heights; explicit hover, active, focus-visible, disabled, and pending states.
- `UiIconButton`: 32×32px visual control with at least a 32×32px hit target, required accessible name, and delayed tooltip; the 24×24px Monaco gutter affordance is the only geometry-specific exception and still meets WCAG 2.2 target minimum.
- `UiBadge`: neutral, accent, warning, destructive, addition, deletion; text/symbol always accompanies color.
- `UiTooltip`: appears on hover and keyboard focus, remains dismissible with Escape, and never contains essential information unavailable elsewhere.
- `UiInlineNotice`: `info`, `warning`, `error`, `success`, with `role="status"` or `role="alert"` selected by urgency.
- `UiDrawer`: non-modal, docked navigation/complementary panel used only at narrower widths; focus is not trapped.
- `UiConfirmRow`: inline confirmation region used for discarding non-empty comment text; no modal confirmation.
- `UiSpinner`: 16px, paired with status copy; motion disabled under `prefers-reduced-motion`.

Radii are geometry tokens, not spacing: `radius-sm: 4px`, `radius-md: 8px`; use `radius-sm` for controls and `radius-md` only for composer/comment/notice surfaces. Shadows are reserved for narrow docked drawers (`0 8px 24px rgb(36 40 34 / 0.16)`); desktop panels use borders, not shadows. Color/background transitions use 120ms `ease-out`; reduced-motion mode removes transitions and spinner rotation.

## Typography

Only four sizes and two weights may appear in application chrome. Monaco code uses the Body size and its own monospace family.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / metadata | 12px | 400 or 600 | 16px |
| Body / controls / Monaco code | 14px | 400 | 20px |
| Heading / active file | 18px | 600 | 24px |
| Display / major empty-error heading | 24px | 600 | 32px |

- Allowed weights: regular `400` and semibold `600` only.
- Repository paths, line numbers, short/full OIDs, shortcut tokens, and side labels use the monospace family at Label or Body size.
- Use tabular numerals for line numbers and additions/deletions.
- Do not uppercase prose. Uppercase is reserved for the compact `BASE` and `HEAD` editor-side labels and one-letter file status badges.
- Truncated safe display paths use a middle ellipsis. The exact lossless path remains available through the existing details/copy affordance; truncation never replaces path authority.

## Screen Architecture and Geometry

### Stable shell

The application owns `100dvh`; the document body does not scroll. The identity header and workspace toolbars remain fixed while the file tree, Monaco sides, and comments rail scroll independently.

1. **Persistent identity header — 64px tall at wide widths.**
   - Left: product label `Diff Review`, then ordered identity `{base label} {short base OID} → {head label} {short head OID}`.
   - Center/secondary: `Reviewing merge base {short merge-base OID} → head` and a `Pinned comparison` badge.
   - Right: `View full identities` button and any locked dirty-worktree badge inherited from Phase 1.
   - The identity detail surface labels and exposes copyable full values for `Base source`, `Base commit`, `Head source`, `Head commit`, and `Merge base`, followed by: `This session is pinned to these commits and does not follow moving refs.`
   - When applicable, show `Dirty worktree ignored` with: `Committed HEAD is reviewed. Staged, unstaged, and untracked bytes are not included.`
   - Do not add a selector-drift badge or polling state; active drift handling is Phase 3.

2. **Primary workspace — three regions on wide screens.**
   - Left `nav` labeled `Changed files`: 288px wide, using the deterministic Phase 1 tree, status/count/path cues, and opaque selection identity.
   - Center `main` labeled `Diff review`: `minmax(640px, 1fr)` and visually dominant.
   - Right `aside` labeled `Comments`: 320px wide, containing accepted verified, stale, and orphaned comment records for this draft. This is a Phase 2 anchor navigation surface, not Phase 3 comment management: no edit, delete, resolve, reopen, filter, or summary controls.

3. **Center workspace chrome.**
   - Active-file strip: 48px. Left shows status badge and safe repository-relative path; renamed/copied files show `old path → new path`. Exact paths remain available through `Path details`.
   - Persistent navigation toolbar: 48px. Group file controls separately from change controls with a rule and text labels, not four indistinguishable icons.
   - Side headers: 32px aligned above each editor. Left: `BASE · merge base {short OID}` and the base-side safe path. Right: `HEAD · {head label} {short OID}` and the head-side safe path.
   - Monaco diff fills the remaining center height and always uses `renderSideBySide: true`, read-only sides, visible glyph margins, synchronized vertical alignment, 14px code/20px line height, and minimap off. No stacked/unified layout or layout toggle exists in Phase 2.

### Responsive rules

| Viewport | Contract |
|----------|----------|
| `≥ 1440px` | Three persistent columns: 288px files, flexible diff, 320px comments. Identity header remains one row. |
| `1100–1439px` | Files remain 256px; comments become a 320px docked right drawer opened by the persistent `Comments` button. The drawer is non-modal and closes with its `Close comments` control or Escape. |
| `768–1099px` | Diff owns full width. Files and comments are mutually independent 288px docked drawers opened by labeled `Files` and `Comments` controls. Active-file and navigation bars remain two fixed 48px rows. Selecting a file closes the file drawer and returns focus to the active-file heading. |
| `< 768px` | Do not switch to a stacked or unified diff. Keep the side-by-side canvas at a 640px minimum inside a horizontally scrollable diff viewport and pin the notice: `Widen the window for the clearest side-by-side review.` Files/comments remain drawers. This is a constrained fallback, not a layout mode. |

At 200% zoom, the same responsive rules apply without clipped buttons or overlapping text. On resize, the editor is laid out in place; models are not recreated and per-file scroll, side/line focus, context expansion, accepted comment zones, and active composer state are preserved.

### Visual hierarchy

1. **Primary focal point:** changed code and the currently focused line in the side-by-side Monaco plane.
2. **Secondary:** active file/path and persistent file/change navigation.
3. **Tertiary:** pinned comparison identity, file tree, and comments rail.
4. **On demand:** the gutter comment affordance and inline composer become the strongest local focus only on the active line; inactive lines never show a field of persistent plus icons.
5. Stale/orphan warnings use semantic amber/red labels but never visually outrank an active recoverable composer error.

## Navigation Contract

### Persistent visible controls

| Control | Visible label | Shortcut | Enabled/disabled behavior and tooltip |
|---------|---------------|----------|---------------------------------------|
| Previous file | `Previous file` | `Alt+Shift+[` | Moves in deterministic changed-file tree order. Disabled at first reviewable entry; description: `First changed file.` |
| Next file | `Next file` | `Alt+Shift+]` | Moves in deterministic changed-file tree order. Disabled at last reviewable entry; description: `Last changed file.` |
| Previous change | `Previous change` | `Shift+F7` | Calls Monaco's public previous-diff navigation. Disabled/no-op with description `No previous change in this file.` |
| Next change | `Next change` | `F7` | Calls Monaco's public next-diff navigation. Disabled/no-op with description `No next change in this file.` |
| Comments | `Comments` | none | Opens/focuses the comments rail/drawer; badge is a neutral total accepted-record count only, not Phase 3 open/resolved lifecycle counts. |
| Keyboard help | `Keyboard help` | `?` outside text inputs | Opens a non-modal help popover containing every documented shortcut below. |

Buttons remain visible peers of shortcuts. Each tooltip includes label plus shortcut, for example `Next change · F7`. Shortcut handling is scoped to the application and must not run while the identity detail/copy control or comment textarea owns an incompatible keystroke. Exact bindings must be validated in supported Chromium on macOS and Windows/Linux during the mandatory Monaco prototype; if a browser/platform intercepts a proposed binding, planning must choose one replacement and update button tooltips, keyboard help, tests, and this contract together before broad UI implementation.

### Keyboard help copy

The help surface title is `Keyboard actions` and contains exactly:

- `Previous file — Alt+Shift+[` 
- `Next file — Alt+Shift+]`
- `Previous change — Shift+F7`
- `Next change — F7`
- `Add or focus comment on current line — Option+Enter on macOS; Alt+Enter on Windows and Linux`
- `Add comment — Command+Enter on macOS; Ctrl+Enter on Windows and Linux`
- `Discard or close composer — Escape`
- `Move through controls — Tab and Shift+Tab`
- `Move within the changed-file tree — Arrow keys; Enter opens a file`
- `Open Monaco accessibility help — Alt+F1`

Footer copy: `Shortcuts never replace the visible controls.`

### Per-file state and switching

Before switching files, snapshot the active file's scroll position, focused side and model line, collapsed-context expansion state, and active composer anchor/text. Restore all four after the new diff is ready. Switching or resizing never blurs-to-submit. Returning A → B → A restores A exactly; an accepted comment remains identified by immutable side model coordinates and server-returned anchor identity, never by DOM node, rendered row, pixel position, view-zone ID, or viewport state.

## Collapsed Context Contract

Unchanged regions of at least 8 lines are collapsed by default, retaining 3 context lines around each change. Expansion state is session-only and remembered per file.

Each collapsed region occupies one aligned neutral band across both sides. It states the exact hidden count, for example `42 unchanged lines`, and exposes:

- `Show 10 lines above`
- `Show 10 lines below`
- `Show all 42 unchanged lines`

When fewer than 10 lines remain, the bounded control uses the actual number (`Show 6 lines above`). At a file boundary, omit the impossible direction rather than disable an unexplained control. Every control is keyboard focusable, uses Enter/Space, and carries the side-independent region label `Collapsed unchanged context, 42 lines`.

The mandatory Monaco prototype decides how these semantics map to Monaco 0.55.1 public APIs. Private contribution IDs or internal view-model fields are forbidden. If public selective reveal cannot expose a durable comment's line, `Show comment` must switch that file into an explicit session-only all-context state, reveal the exact model line, and then focus the comment. That fallback may reveal more context but may not relocate the anchor. The workspace may show the quiet status `All context revealed to show this comment.`

## Comment Creation and Inline Composer

### Gutter affordance

- Hovering a visible line gutter, or focusing/cursoring a visible line in either side editor, reveals one 24×24px `+` button on that exact side and model line.
- Accessible names are exact and side-specific: `Add comment to base line 42` or `Add comment to head line 47`.
- Tooltip copy matches the accessible name and appends the keyboard action: `Add comment to base line 42 · Option+Enter` (macOS) or `· Alt+Enter` (Windows/Linux).
- Activating the button or keyboard action calls the same model-coordinate action. It never derives side or line from a rendered row index.
- If that side-specific line already has a comment, activation does not open a new composer; it reveals and focuses the accepted comment, and the accessible name becomes `Focus comment on base line 42`.

### Inline geometry

The composer is inserted directly below the anchored model line on the selected side. It uses an editor-owned paired view-zone strategy: the active side contains the composer and the opposite side receives an `aria-hidden` alignment spacer of exactly the same measured height. Both zones update together as text grows. A 2px semantic accent rule connects the selected gutter line to the composer without covering code.

- Composer width: the selected editor content width between gutter and scrollbar, with `md` inset.
- Minimum body height: three 20px text lines plus `sm` vertical insets; maximum visible body height: 240px, after which the textarea scrolls.
- Composer surface: elevated token, rule border, `radius-md`; no shadow inside Monaco.
- Only one composer may be active per file. Activating a different line while the existing composer is empty moves it. If it contains text, show the same inline discard confirmation before moving. Other files retain their own active composer/text in session memory.

### Locked header fields

The 32px composer header is read-only and shows, in this order:

1. side-specific safe repository-relative path;
2. `Base` or `Head`;
3. `line {number}`;
4. a lock glyph with tooltip `Anchor fields are fixed for this comment.`

Example visible header: `src/auth/session.ts · Head · line 47`. For a rename, the base composer shows the old path and the head composer shows the new path. Exact path details remain copyable through `Path details`. Path, side, line, blob identity, selected text, nearby context, and context hash are never editable browser fields; the server derives the durable record from the opaque file capability plus side and line.

### Composer body and actions

- Textarea label: `Comment`.
- Placeholder: `Describe the issue or requested change…`
- Supporting copy: `Your comment is accepted only after it is saved locally.`
- Primary button: `Add comment`.
- Secondary/destructive quiet button: `Discard draft`.
- `Command+Enter` (macOS) or `Ctrl+Enter` (Windows/Linux) invokes `Add comment`.
- Blur only preserves text; it never submits or discards.
- Whitespace-only acceptance keeps the composer open and shows `Write a comment before adding it.` associated with the textarea.

### Discard path

- Escape or `Discard draft` closes an empty composer immediately and returns focus to the originating line's gutter affordance.
- With non-empty unaccepted text, replace the footer with an inline `UiConfirmRow`:
  - Prompt: `Discard this comment draft? Your text hasn’t been saved.`
  - Safe action: `Keep writing`
  - Destructive action: `Discard draft`
- Escape while the confirmation row is open chooses `Keep writing` and returns focus to the textarea. Only explicit `Discard draft` removes non-empty text.

## Persistence, Acceptance, and Failure States

A comment is not visually or semantically accepted until the atomic repository-local write succeeds and the server returns the canonical accepted record.

| State | User-visible treatment | Exact copy / focus behavior |
|-------|------------------------|-----------------------------|
| Ready | Editable inline composer; `Add comment` enabled only for non-whitespace text | Supporting copy: `Your comment is accepted only after it is saved locally.` |
| Pending atomic write | Composer and anchor remain in place. Textarea and both actions are temporarily disabled; button shows spinner plus `Adding comment…`. | Polite live region: `Adding comment to {side} line {line}…` No accepted comment, saved badge, or success toast appears. |
| Accepted | Replace composer with an inline accepted-comment surface at the exact side/line; add/update its comments-rail record. Focus moves to the accepted comment heading. | Live region: `Comment added and saved locally on {side} line {line}.` Comment header badge: `Saved locally`. |
| Recoverable persistence failure | Keep exact composer anchor and all text in place; re-enable editing/actions; show inline `role="alert"` above footer. | `Comment wasn’t added. Your text is still here. Check that Diff Review is running, then try again.` Primary action remains `Add comment`. |
| Duplicate reported by server | Do not accept a duplicate. Refresh/focus the canonical existing record if available. | `A comment already exists on this line. Opening it instead.` Then focus that comment. If canonical refresh fails, keep text and use the recoverable failure state. |
| Session ended while adding | Keep text in memory and show a terminal recovery path without claiming persistence. | `Comment wasn’t added because this review session ended. Your text is still here. Relaunch Diff Review from the repository before trying again.` |

No auto-retry, optimistic accepted card, blur submission, duplicate thread, reply affordance, edit/delete/resolve control, or summary input is present in Phase 2.

### Draft load and resume copy

- While loading: `Opening local draft…`
- Same pinned commit pair with a valid existing draft: status notice `Local draft resumed. Accepted comments for this pinned comparison are ready.`
- Same pinned pair with no accepted comments: status notice `New local draft for this pinned comparison.`
- A different selected base or head commit receives its own draft and uses the same `New local draft for this pinned comparison.` copy; the UI never merges or offers another pair's comments.
- Valid draft-load failure that prevents safe review: heading `Local draft couldn’t be opened`; body `Existing review data was left unchanged. Relaunch Diff Review or check the terminal for details.` This state does not overwrite the file or silently start empty. Full corrupt-schema recovery controls remain Phase 3.

## Accepted Comments, Reveal, and Focus

### Inline accepted comment

A verified accepted comment uses the same paired-zone alignment strategy as the composer. Its immutable header shows safe path, `Base`/`Head`, `line {number}`, and `Saved locally`. The body is selectable text. It has no kebab menu and no lifecycle actions in Phase 2.

### Comments rail

The rail title is `Comments`. It lists accepted records in deterministic file-tree order, then side (`Base` before `Head`), then side-specific line. Each record shows:

- safe repository-relative path;
- `Base line {n}` or `Head line {n}`;
- first two body lines, visually truncated without changing the accessible name;
- one state badge: `Saved`, `Stale anchor`, or `Anchor unavailable`;
- one explicit action described below.

Empty rail:

- Heading: `Start with a line`
- Body: `Choose a line in the diff, then use the + gutter button or Option+Enter on macOS; Alt+Enter on Windows and Linux.`

### Verified `Show comment` sequence

The action label is `Show comment`. Activation must:

1. preserve the current file's scroll/focus/context/composer state;
2. select the comment's file through its opaque file identity;
3. wait for the immutable side models and diff update;
4. reveal the anchored line—expanding the bounded region or the public all-context fallback if needed;
5. reconstruct the paired comment zones from the exact side/model line;
6. scroll the anchored line into the center third of the viewport;
7. move DOM focus to the inline comment heading (`tabindex="-1"`), not merely the editor;
8. announce `Showing comment on {side} line {line} in {safe path}.`

If already visible, do not reset scroll more than necessary. Escape from a focused inline comment returns focus to the `Show comment` action that initiated navigation.

## Stale and Orphan Contract

Verification has exactly three user-visible states. It never searches nearby lines, chooses a best match, changes a recorded line, rewrites the anchor, or silently decorates another line.

| State | Placement | Badge and exact copy | Action |
|-------|-----------|----------------------|--------|
| Verified | Inline on exact side/model line and in comments rail | `Saved` | `Show comment` performs reveal/focus sequence. |
| Stale | Comments rail only; no inline comment or gutter marker | Badge: `Stale anchor`. Body: `Anchor no longer verifies. The pinned text or context does not match this comment’s recorded anchor. It has not been moved.` Show recorded safe path, side, line, and short blob ID beneath. | `Inspect recorded file` selects the exact recorded file when still available but keeps focus on the stale rail record; it does not place the comment. `Copy anchor details` copies the recorded immutable details. |
| Orphaned | Comments rail only; no inline comment or gutter marker | Badge: `Anchor unavailable`. Body: `The recorded file, blob, side, or line can’t be opened in this pinned comparison. The comment is preserved and has not been moved.` Show every recorded detail that remains safe/available. | `Copy anchor details`. If the exact file capability is still available, additionally show `Inspect recorded file`; otherwise no fabricated navigation target appears. |

Stale/orphan records remain visually equal in body readability to verified comments. They are not hidden in a toast or dropped from the rail. Amber/red color is reinforced by badge text and warning icon. Phase 2 offers no reattach, edit, delete, resolve, or dismiss action.

## Loading, Empty, Error, and Disabled States

| Surface | Exact state contract |
|---------|----------------------|

## Accessibility Contract

### Structure and names

- Landmarks: `header` (`Pinned comparison`), `nav` (`Changed files`), `main` (`Diff review`), and `aside` (`Comments`). One visible `h1` is the active safe file path; panel titles are `h2`.
- First focusable elements are skip links: `Skip to changed files`, `Skip to diff`, and `Skip to comments`.
- Monaco accessible labels are side-specific: `{safe path}, base side, read-only diff` and `{safe path}, head side, read-only diff`. The enclosing label is `{safe path}: base and head side-by-side diff`.
- `BASE`/`HEAD`, status letters, additions/deletions, stale/orphan state, and dirty/pinned identity all have full accessible text; no meaning relies on color, arrow direction, or icon shape alone.
- The file tree follows the ARIA tree pattern only if the implementation can satisfy its full keyboard contract; otherwise use nested lists with buttons. Do not apply `role="tree"` to visually nested markup without roving focus and Arrow key behavior.

### Focus and keyboard

- Focus-visible style: 2px `--accent` ring plus 2px canvas offset; never remove Monaco's cursor/focused-line indication without an equivalent.
- Tab order follows visible structure and never enters alignment spacers. Comment zones, collapsed-context controls, tooltips, drawers, and confirmations are fully keyboard operable.
- Opening a drawer moves focus to its heading; closing returns focus to its trigger. Drawers are non-modal and do not trap focus.
- Opening a composer moves focus to `Comment`. Successful acceptance focuses the accepted comment heading. Persistence failure focuses the alert only if the user initiated acceptance, then the next Tab returns to the textarea; screen-reader users retain context.
- Keyboard-triggered gutter activation always uses the focused editor side and cursor model line. If no valid visible model line is focused, the action is unavailable and announces `Focus a line in the diff before adding a comment.`
- Monaco `Alt+F1` accessibility help remains available and is listed in app help.

### Announcements

Use one polite live region for loading, navigation, context reveal, draft resume, and successful saves; use an assertive `role="alert"` only for failed persistence/session access. Do not announce every cursor movement or hover affordance.

Exact announcements include:

- `Loaded {safe path}. Base has {n} lines; head has {m} lines.`
- `Showing next change, head line {n}.`
- `Revealed {n} unchanged lines.`
- `Showing comment on {side} line {line} in {safe path}.`
- `Comment added and saved locally on {side} line {line}.`

### Contrast, zoom, motion, and target size

- All normal text meets WCAG AA 4.5:1; large text and non-text UI boundaries meet 3:1.
- At 200% zoom, drawers replace fixed side rails before labels clip; toolbars wrap only at declared responsive boundaries.
- Default control hit targets are at least 32×32px. The gutter comment target is 24×24px with sufficient separation and no adjacent competing target, satisfying WCAG 2.2 Target Size (Minimum).
- Respect `prefers-reduced-motion`: remove transitions and replace rotating spinner motion with a static progress glyph plus text. No content depends on animation.
- Tooltips are hoverable, focusable through their trigger, dismissible with Escape, and never the sole documentation path.

## Interaction and Boundary Matrix

| Decision / boundary | Contract coverage |
|---------------------|-------------------|
| D-01 | Hover/focused-line gutter affordance plus documented Option/Alt+Enter action; same activation path. |
| D-02 | Inline side-specific composer directly below line; locked safe path, side, and line header. |
| D-03 | One comment per side/model line; duplicate activation and server conflict focus the canonical existing comment. No threads/replies. |
| D-04 | Explicit `Add comment` and Command/Ctrl+Enter only; blur preserves without submitting. |
| D-05 | Empty Escape/discard closes immediately; non-empty text requires inline `Keep writing` / `Discard draft` confirmation. |
| D-06 | Pending composer remains unaccepted; only atomic success yields accepted UI; failures preserve text and anchor. |
| D-07 | One active file only; no stacked file diff, unified diff, or layout toggle. |
| D-08 | Unchanged regions collapsed by default with bounded 10-line and all-region controls. |
| D-09 | Expansion state per file; `Show comment` reveals hidden anchor before focus, with public all-context fallback. |
| D-10 | Persistent previous/next file and change buttons, shortcuts, tooltips, and keyboard-help copy. |
| D-11 | Scroll, side/line focus, expansion, and active composer survive file switching and resize. |
| D-12 | UI placement keys are immutable file/blob/path/side/model-line facts; never pixels, rows, viewport, DOM, or view-zone IDs. |
| CMT-08 | Verified/stale/orphan states remain visible; stale/orphan comments stay in the rail and are never silently relocated. |
| DRFT-02 / DRFT-03 | Same pair resumes with explicit copy; a changed base or head receives separate new-draft copy and no merged state. |
| Later-phase boundary | No edit, delete, resolve/reopen, summary, conflict management, active selector drift, export, reattachment, stacked files, threads, or layout/theme toggle. |

### Mandatory stability gate before broad workspace implementation

A production-shaped real-Monaco prototype must prove that the visual contract survives: comments on base/head changed and unchanged lines; bounded/all context reveal; composer/comment zone growth; resizing; A → B → A state restore; at least ten diff recomputations/model swaps; keyboard and pointer parity; deterministic file/change navigation; hidden-comment reveal using public APIs; no duplicated zones/listeners/models; and no anchor movement. If Monaco cannot satisfy paired side alignment with public view zones, the permitted fallback is one full-width synchronized row immediately below the anchored diff row, visibly identifying the selected side. Overlaying code, attaching by pixels, using private Monaco members, or silently relocating the anchor is not an acceptable fallback.
