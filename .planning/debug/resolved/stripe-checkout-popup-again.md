# Debug: stripe checkout popup again

## Symptoms

- **Expected:** after a completed Stripe Checkout (user confirmed to exist as a customer in Stripe), the local support state becomes `verified` and the launch support prompt stops appearing on subsequent `cumpa` launches on that machine.
- **Actual:** the support dialog reappeared in `invitation` mode on a later launch. Immediately after checkout the dialog stayed on `waiting` ("Waiting for confirmation… You can close this and keep reviewing.") and never flipped to `verified`/`thankYou`.
- **Errors:** none observed; terminal output and browser devtools were not checked, so absence of an error is unconfirmed.
- **Timeline:** first observed on this purchase. No prior verified state exists on the machine.
- **Reproduction (as reported):**
  1. Launch Cumpa from the published npm package (`@shipwithai/cumpa`, global/npx — not a local dev build).
  2. Open the support dialog, click "Support Cumpa — $49.99", complete Stripe Checkout in the browser (payment succeeded; customer record exists in Stripe).
  3. Dialog remains on "Waiting for confirmation…".
  4. Later, launch Cumpa again on the **same machine** but in a **different repository/worktree** → support prompt shows again in invitation mode.
- **Not yet tried:** the dialog's "Restore support" button (untested since paying — an important discriminator between the post-checkout poll path and the hosted entitlement/binding state).

## Resolution

root_cause: A 100%-off promotion code produces a Stripe Checkout Session with `payment_status: no_payment_required`, `amount_total: 0`, and no PaymentIntent, and `RetrievedCheckoutSchema` in `supabase/functions/_shared/fulfillment.ts` required `payment_status: "paid"`, `amount_total >= 1`, and a non-empty `payment_intent`. `checkoutSessionInvariant` therefore returned `undefined`, `stripe-webhook` answered 400 before settlement, `fulfill_checkout_session` never ran, and no `support_private.installation_bindings` row was written — so `support_private.installation_status` (a bare `EXISTS` over that table) kept answering false and every `/api/support/refresh` correctly reported `unverified`. The reappearing launch prompt was the faithful rendering of that hosted truth; the local machine-scoped store and the 1.6.0 client were never at fault. The state was structurally unrecoverable: `support_private.supporters.stripe_payment_intent_id` was `NOT NULL`, so a comped supporter had no representable row even if the invariant had allowed one.
fix: Comped support is now a first-class fulfillment outcome. `RetrievedCheckoutSchema` became a union of a paid shape (`payment_status: "paid"`, `amount_total` 1..4999, non-empty `payment_intent`) and a comped shape (`payment_status: "no_payment_required"`, `amount_total: 0`, null/absent `payment_intent`), sharing one `CheckoutIdentitySchema` that still pins payment mode, USD, `amount_subtotal === 4999`, exact price id, quantity 1, server-owned metadata, and a non-empty Customer; `VerifiedCheckout.paymentIntentId` is now `string | null`. Migration `20260916000000_comped_support_fulfillment.sql` drops `NOT NULL` from `supporters.stripe_payment_intent_id` and replaces `fulfill_checkout_session` so a NULL PaymentIntent is valid input and the `supporter payment conflict` guard raises only when two *charged* PaymentIntents differ — a comped supporter can later pay, and two distinct charges for one supporter still conflict.
verification: RED at the function layer — the new Deno test `a fully discounted comped session settles without a PaymentIntent` failed with `expected 200, received 400` and zero RPC calls, reproducing production exactly. RED at the database layer — with the migration moved aside, `npx supabase test db` failed tests 45-46 (`have: false, want: true`), proving the migration is load-bearing. GREEN after the fix — `deno test --allow-env --config supabase/functions/deno.json supabase/functions/tests` 20/20 passed (including the paid path, the non-zero discount path, every forgery rejection, idempotency, and retryability), `npx supabase test db` 49/49 passed, `npx supabase db lint --local` reported no schema errors, and all three migrations applied cleanly from `db reset`. The test that pinned the opposite contract (`a 100%-off session has no PaymentIntent to audit and is rejected before settlement`) was deleted rather than re-pinned, and replaced by `a comped session still needs the exact list subtotal, price, and a real customer`, which holds every remaining anti-forgery field.
