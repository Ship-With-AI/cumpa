# Phase 07 — UI Design Contract

> Visual and interaction contract for Phase 07: GitHub-Familiar Review Surfaces. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Contract Boundary

Phase 07 adapts the existing file context header, toolbar, inline comment surfaces, notices, Summary, Export, and review rail to the established dark review language. It is a presentation adaptation over the shipped local review workflow, not a new review model.

Locked decisions D-01 through D-16 in `07-CONTEXT.md` are authoritative. This contract resolves only the areas explicitly left to the agent’s discretion. It inherits the exact semantic tokens, typography, spacing, shape, focus, and state vocabulary from Phase 05 and the Monaco layering, anchor rail, paired-zone, and geometry invariants from Phase 06.

Implementation MUST preserve all current events, labels unless this contract explicitly records a presentation-only label change, keyboard commands, tooltips, ARIA relationships, focus destinations, disclosures, mutation and disable rules, persistence, draft revisions, export transitions, file ordering, Summary → Open → Resolved → Export order, and side-by-side Monaco behavior. Existing source classes and Vue components are the integration seam; presentation MUST remain centralized in `src/web/styles.css`.

Phase 08 owns final proof at narrow widths, 400% zoom, grayscale, forced colors, and across the complete end-to-end workflow. Phase 07 MUST avoid blocking those boundaries and MUST perform focused browser proof of its own states, but MUST NOT claim Phase 08 requirements complete.

### Source Precedence

1. `07-CONTEXT.md` locked decisions and phase boundary.
2. `REQUIREMENTS.md` VIS-04 and REVW-01 through REVW-04.
3. `07-RESEARCH.md` verified implementation seams and preservation rules.
4. Phase 05 and Phase 06 UI contracts for inherited visual and Monaco behavior.
5. Current Vue templates and `src/web/styles.css` for exact copy, state transitions, ARIA, and component hooks.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none; retain existing Vue 3 components and native elements |
| Icon library | none; local inline SVG only |
| Font | Local system UI: `-apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`; code/IDs/paths: `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace` |
| Styling | Existing native CSS in `src/web/styles.css`; reuse the single inherited semantic token root and BEM-like hooks |
| Third-party registry | none |

No shadcn initialization, Primer runtime, remote font, remote icon, remote asset, CSS framework, icon package, or third-party registry is permitted. Local SVG glyphs use `currentColor`, a 16×16 view box, 1.5px stroke, round line caps and joins, and no embedded text. Decorative SVGs are `aria-hidden="true"`; the native button or adjacent visible label carries the accessible name.

## Spacing Scale

All spacing MUST use the inherited 4-point scale. New component-specific near-duplicate tokens are prohibited.

| Token | Value | Phase 07 usage |
|-------|-------|----------------|
| `space-xs` | 4px | Icon-to-label gap, badge inline padding, dense metadata gap |
| `space-sm` | 8px | Compact control padding, toolbar and action gap, card subregion inset |
| `space-md` | 16px | Header/context inset, card body inset, rail section gap |
| `space-lg` | 24px | Separated recovery or confirmation content only |
| `space-xl` | 32px | Existing shell/drawer-safe layout only |
| `space-2xl` | 48px | Major state separation only; not routine review-surface padding |
| `space-3xl` | 64px | Existing workspace/header geometry only; no new component uses it |

### Density Rules

- Header context band: 8px block padding and 16px inline padding; 16px between Base/path/Head columns.
- Toolbar band: 8px block padding and 16px inline padding; 8px between actions; 8px padding plus a 1px divider between existing action groups.
- Conversation-card header and footer: 8px block and 16px inline padding. Body: 16px block and inline padding.
- Rail major sections: 16px internal padding and 16px between sibling sections.
- File-group header: 8px block and 16px inline padding. Comment rows: 8px block and 16px inline padding; adjacent rows use one 1px divider, not independent margins and frames.
- Buttons and single-line fields retain a minimum 32px block size. Icon-only toolbar buttons are exactly 32×32px with a visible 16px glyph.
- Textarea minimums remain behavior-compatible: composer 76px; summary and rail edit fields 96px. Existing resize and measured view-zone growth remain authoritative.
- Confirmation action groups use 8px gaps and may wrap; destructive and escape actions MUST NOT become adjacent without a visible gap.

**Exceptions:** 1px borders/dividers, 2px focus outlines, 2px Monaco change bars, 3px selected/anchor rails, 1.5px SVG strokes, and 4px/6px/8px/999px radii are visual dimensions rather than spacing. No spacing exception may use a non-4px value.

## Typography

Exactly four interface sizes and exactly two weights are permitted. Phase 07 MUST NOT introduce another size or weight.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Metadata / badge | 12px | 400 or 600 | 16px |
| Body / controls | 14px | 400 or 600 | 20px |
| Section heading | 16px | 600 | 24px |
| Page/state heading | 20px | 600 | 28px |

### Typography Rules

- Allowed weights are regular `400` and semibold `600` only. No `500`, `700`, synthetic bold, or italic status text.
- Body line-height is 20px. Heading line-heights are 24px and 28px according to role.
- File names, selected comment headings, section headings, and active labels may use 600; directories and supporting metadata use 400.
- Paths, seven-character OIDs, full hashes, revision numbers, line anchors, and receipt paths use the inherited monospace stack at 12px/16px or 14px/20px according to hierarchy.
- `BASE` and `HEAD` use 12px/16px semibold, uppercase, with letter spacing no greater than `0.04em`. Uppercase is not used for general headings or buttons.
- Directory segments use `text-muted`; filename segments use `text-primary` and 600. For a renamed/copied file, both old and new filenames remain stronger than their directory segments and the arrow remains secondary.
- Truncation is allowed only when the complete value remains available through existing `title`, accessible name, disclosure, or copy action. Comments, error text, validation, guidance, and receipt metadata wrap with `overflow-wrap: anywhere` rather than disappear.

## Information Architecture and Hierarchy

The outer information architecture is unchanged. The active diff remains the primary focal area. The grouped header supplies file/comparison context; the file tree and review rail remain supporting regions.

### Grouped File Context Header

The header is one outer `.review-context-header` with two semantic bands:

1. **Context band:** Base endpoint, active file identity, Head endpoint, plus the conditional existing `Files` drawer control where applicable.
2. **Toolbar band:** existing File navigation group, Change navigation group, Review action, and Keyboard help action.

At desktop widths the context band uses a three-column grid: `minmax(144px, 1fr) minmax(200px, 2fr) minmax(144px, 1fr)`. Base aligns to the left diff pane; Head aligns to the right. The file identity remains the center and strongest context. The implementation MUST use `minmax(0, …)` and `min-width: 0` so long values do not force document overflow.

Endpoint block anatomy is exact:

- First line: visible `BASE` or `HEAD`, 12px/16px semibold.
- Second line: the existing safe selector label, 14px/20px regular.
- Third inline datum: the established first seven characters of the OID, 12px/16px monospace. The complete OID remains available through existing comparison identity details or a full-value title.
- The UI MUST NOT re-resolve refs, normalize Git paths, or infer another identity.

Active path anatomy:

- Normal path: quiet directory segment(s), then semibold filename.
- Renamed/copied path: complete safe old path, visible `→`, complete safe new path; both filenames lead their respective paths. Preserve the existing accessible label `renamed/copied from … to …` and safe display data.
- Deleted files use the old path; other files use the current effective path, matching existing `PathDisplay` behavior.
- `Diff review` remains quiet metadata, not a competing page heading.

### Toolbar

- Keep all six current actions, emits, tooltips, shortcut copy, `aria-controls`, `aria-expanded`, count description, and native disable expressions.
- Previous/next file and previous/next change become icon-only 32×32px buttons. Their programmatic names and focus/hover tooltips use the existing action wording and shortcuts exactly.
- `Review` and `Keyboard help` remain visibly labeled 14px controls. Review may add a comment-count badge but MUST retain the existing screen-reader description with both open and resolved counts.
- When the review rail is expanded, Review receives the selected/current contract: stronger neutral surface, accent rail or border, and existing `aria-expanded="true"`. Focus remains a separate 2px outer ring.
- The conditional `Files` drawer action remains visible in the context band at existing drawer widths.

## Interaction State Contract

Every existing diff-workspace control MUST map to this state matrix. A component MAY not invent a one-off state treatment.

| State | Exact visual response | Behavior and semantics |
|-------|-----------------------|------------------------|
| Rest | `surface-interactive`, `border-default`, `text-primary` | Existing click, keyboard, and command behavior unchanged |
| Hover | `surface-interactive-hover` + `border-strong` | Enabled pointer targets only; no hover-only information or movement |
| Pressed | `surface-interactive-active` + `border-strong`; no inset shadow | Existing activation semantics; bounds and label position stable |
| Selected/current | `surface-raised` plus persistent 3px accent rail or strong accent boundary and visible text/icon meaning | Existing `aria-expanded`, `aria-selected`, or presentation-only selected label remains independent from focus |
| Focus-visible | opaque 2px `focus-ring` outline with 2px offset, outermost | Keyboard focus only; never clipped, obscured, or replaced by selected/status styling |
| Disabled | `status-disabled-background`, muted foreground, `border-default`, no hover response | Existing native `disabled` or ARIA state and mutation rules; no opacity-only treatment |
| Destructive rest | neutral interactive surface with `destructive-foreground` text/icon/border | Destructive intent visible before activation |
| Destructive hover/press | `destructive-emphasis`, `text-on-emphasis`, destructive border | Existing confirmation and Escape/cancel path retained |
| Busy | disabled neutral geometry, reserved spinner, exact progressive verb | Existing disable rules; local `aria-busy` where appropriate and existing status/live announcement; never implies completion |

### Action Tiers

- **Neutral outlined:** navigation, Review, Keyboard help, Cancel, Keep, Copy, Reveal, Reload, Retry, Show, Edit, Resolve/Reopen, and gitignore choices.
- **Filled accent:** only the primary action in the active task region: `Add comment`, `Save comment`, `Save summary`, `Export review`, `Export pinned review`, or `Open new draft`. Do not promote passive disclosures or gitignore consent to primary.
- **Destructive outlined at rest:** `Discard draft`, `Discard changes`, `Delete comment`, and `Back up and start new`. Emphasis fill appears only on hover/press or within an already explicit confirmation region.

Busy presentation is localized to the acted-on control or row. An operation-wide `pending` value MUST be paired with the current comment ID before showing `Resolving…`, `Reopening…`, or `Deleting…`; other rows remain merely disabled and MUST NOT falsely appear in progress.

## Inline Comment Surface Contract

### Conversation-Card Anatomy

Both composer and accepted comment use the same flat contained anatomy inside the existing Monaco view zone:

1. **Metadata header:** filename first, then `Base line {N}` or `Head line {N}`; lifecycle badge and anchor badge align at the trailing edge. The directory appears below or before the filename as quiet supporting metadata. The existing lock cue and fixed-anchor explanation remain available.
2. **Body:** comment text or the labeled textarea. Body copy wraps; no fixed card height or hidden overflow.
3. **Field support:** the existing saved-locally guidance sits directly below the textarea. Validation and operation failure sit immediately after that guidance, are explicitly related to the field, use error icon/edge/text, and retain `role="alert"`.
4. **Action footer:** a 1px top divider separates controls. Primary action leads; cancel/destructive action remains visible. Controls wrap without overlapping.

The card uses `surface-panel`, a 1px `border-default`, 6px radius, and no shadow. Header and footer may use a quiet neutral step but MUST NOT use lifecycle color as a full-card fill.

### Lifecycle and Anchor Independence

- Lifecycle is always one of visible `Open` or `Resolved`.
- Anchor status is independently one of `Verified`, `Stale anchor`, or `Anchor unavailable`.
- `Open` remains prominent. `Resolved` uses the purple/check treatment and a quieter neutral body; it is not faded with opacity.
- `Stale anchor` and `Anchor unavailable` use warning structure and retain the recorded path/OID/selection details and exact explanatory copy.
- The existing Monaco source-line anchor is always the 3px blue rail on the source line. A lifecycle or anchor badge MUST NOT replace, move, recolor, or duplicate it.
- The counterpart spacer remains `aria-hidden`, neutral, non-interactive, and exactly paired in height.

### Composer States

| State | Contract |
|-------|----------|
| Ready | Visible label `Comment`, support text, `Add comment`, and `Discard draft` |
| Empty validation | Field-adjacent `Write a comment before saving it.` or current composer validation; error icon/edge and alert semantics |
| Persistence failure | Existing failure text remains adjacent and the textarea retains the user’s text |
| Pending | Textarea disabled by the existing rule; primary label `Adding comment…` with spinner; card/field marked busy without layout jump |
| Confirm discard/move | Existing confirmation copy, `Keep writing`, and `Discard draft`; Escape/focus behavior retained |
| Accepted | `Saved locally` remains visible supporting state; lifecycle and anchor badges are separate |

The visual refactor MUST keep the existing measurement loop and `setAnchorZoneHeight(Math.max(280, contentHeight + 16))` contract unless focused browser measurements prove a safe adjustment. It MUST NOT add a second zone, absolutely position content outside the zone, change code origin, change the 50/50 panes, or alter the existing focus handoff.

## Review Rail Contract

### Major Hierarchy

The rail retains this exact order:

1. Rail heading `Review`, labeled `Open {N}` and `Resolved {N}` badges, and `Close review`.
2. Conflict or operation-failure notice when present.
3. Summary framed section.
4. Open comments framed section and disclosure with its count.
5. Resolved comments framed section and disclosure with its count.
6. Export framed section.

Each major section owns one 1px frame and flat `surface-panel` interior. There is 16px between sections. Do not wrap each comment in another card frame.

### File Groups and Comment Rows

- Each path group owns one 1px `border-default` frame and 6px radius.
- Group header leads with quiet directory and semibold filename, followed by the exact group count.
- Rows have no own border, radius, or shadow; `article + article` receives a 1px divider.
- Row heading leads with filename plus Base/Head line anchor. Body follows. Lifecycle and anchor badges are separate.
- Existing action labels remain exact: `Show comment`, `Edit`, `Resolve`, `Reopen`, and `Delete`.
- `Show comment` and `Edit` remain disabled when the anchor is not verified. Warning support, inspect-when-available, and `Copy anchor details` remain visible; the UI MUST NOT guess or relocate an anchor.

### Selected Comment

When an existing `focus-comment` command selects a rail comment, the matching article receives all of:

- persistent 3px `selection-border` rail on the inline start edge;
- `surface-raised` rather than a blue status fill;
- semibold primary heading;
- visible `Selected` badge.

Selection persists after keyboard focus moves and clears only when another focus-comment command selects another comment or the selected comment no longer exists. It is presentation-only and is not persisted. The focusable heading/button retains its separate outer focus ring. Selection MUST remain distinct from Open/Resolved, stale/unavailable, destructive, hover, and busy states.

### Empty Rail States

- Open heading: `No open comments`
- Open body: `Add a comment from a line in the diff, or reopen one from Resolved comments.`
- Resolved heading: `No resolved comments`
- Resolved body: `Resolved comments will remain available here.`

Empty states remain inside their framed section with an informational icon and plain guidance; they do not receive a large illustration or primary CTA.

## Notice and Badge Contract

### Full Notice

Every full notice uses a four-part grid: 16px tone icon, heading, body/recovery content, and 3px leading edge. Icon aligns with the first heading line; body and actions align under the heading. A notice without an explicit semantic heading MUST gain one from the current state branch rather than rely on a border color.

- `role="alert"`: blocking failures, stale acknowledgement, conflicts, corrupt/read-only recovery failure, and validation requiring immediate attention.
- `role="status"` or existing live region: pending stages and non-blocking copy/reveal outcomes.
- `role="note"` or no live role: persistent readiness and explanatory guidance.

Do not add a second live region when an existing status/session announcement already covers the operation. Focus moves only where current components already move it: conflict/failure/recovery/receipt headings.

### Compact Badge

Badges use 12px/16px text, 600 for state label, a 16px icon, 4px icon gap, 4px block and 8px inline padding, 1px border, and 999px radius. Labeled count badges use `Open {N}` and `Resolved {N}` rather than bare numbers. A badge is informational, not a button, unless current semantics already make the containing disclosure operable.

## Summary and Export Surface Contract

### Summary

- Summary remains the first framed rail section.
- Its disclosure preserves exact `aria-expanded`/`aria-controls` behavior and visible state label.
- Edit and Preview retain the existing tab model. Selected tab uses a persistent accent boundary plus `aria-selected`; focus uses the separate outer ring.
- `Review summary (Markdown)` remains a visible label. Guidance and validation/failure remain adjacent.
- Busy save uses spinner + `Saving summary…` in the button and the existing status announcement. Other controls follow current disable rules.
- Discard confirmation remains contained and exact: `Discard unsaved summary changes?`, `Your saved summary will stay unchanged.`, `Keep editing`, `Discard changes`.

### Intentional Export Action

Export never occurs on opening the rail, saving a comment/summary, reloading a revision, checking ignore status, appending `.gitignore`, or acknowledging drift alone. The user MUST activate one explicit primary action:

- Ready: `Export review`
- Already exported: `Export review again`
- Drift acknowledged: `Export pinned review`
- Failed: neutral recovery action `Try export again`

Support copy remains exact: `Creates review.json and review.md together from accepted revision {revision}. This does not apply, stage, commit, or push changes.`

### Readiness and Non-Actionable Records

The readiness summary retains `Accepted revision`, `Open actionable`, `Need reviewer attention`, `Resolved`, `Summary`, and `Ignore status` as labeled values.

- Only open comments with verified anchors are actionable requests.
- Resolved comments remain historical, non-actionable records in export.
- Stale and unavailable/orphaned anchors are exported as non-actionable records. The applying agent is explicitly instructed not to guess or relocate them.
- These classifications do not remove existing in-app lifecycle, delete, inspection, or copy controls. The badge/status itself and the comment row are not turned into generic click targets.

Exact attention copy remains: `Stale or unavailable anchors will be exported as non-actionable records. An applying agent is instructed not to guess or relocate them.`

### Stale Revision and Conflict

If the accepted draft revision is no longer current:

- Show error notice heading `Review changed before export`.
- State both expected and actual revision.
- State exactly that nothing from the attempt was published.
- Offer neutral `Reload latest`.
- Preserve the warning: reloading adopts the latest accepted review and does not export automatically.

A conflict never displays a success receipt for the failed attempt.

### Selector Drift Without Refresh

Selector drift is an acknowledgement gate over the original pinned comparison, not a refresh requirement.

- First drift heading: `Confirm export of pinned review`.
- Explain that current selector targets changed and export still uses original pinned commits.
- Show Base and Head pinned identity plus current moved/unavailable observation.
- Require an unchecked-by-default checkbox with exact consent: `I understand this export remains pinned to the original commits and records the selector drift.`
- Keep `Export pinned review` disabled until checked.
- Offer `Cancel export`.
- Do not require, imply, or perform a source refresh before the user can acknowledge and export the pinned comparison.
- If selectors change again, invalidate the acknowledgement and show `Selected sources changed again`; the user MUST review and acknowledge the latest observation again. Never export automatically after acknowledgement.

### Corrupt and Read-Only Draft State

When the repository-local draft is malformed, schema-invalid, or from a newer unsupported schema, the review remains read only and export MUST NOT be presented as available.

- Visible badge: `Read only`.
- Recoverable heading: `Local review draft needs recovery`; explain that the existing file has not changed.
- Newer-schema heading: `This draft needs a newer Diff Review`; retain the found/supported version and upgrade guidance.
- Show the draft path and explicit problem details; offer `Reveal draft file` and `Copy draft path`.
- Recovery is destructive and explicit: `Back up and start new`, then confirmation `Start a new draft?` with byte-for-byte backup and no-undo text.
- Never replace existing bytes until the backup is verified. Failure states say the draft is still read only and was not replaced.
- A recovered receipt shows the verified backup path with `Copy backup path`; `Open new draft` is the only primary continuation.

### Gitignore Consent

Diff Review MUST NOT alter `.gitignore` automatically, as a side effect of export, or by replacing existing bytes.

- If not ignored, export remains available and the notice explains that generated files may appear untracked.
- Offer neutral choices `Add to .gitignore` and `Keep .gitignore unchanged`.
- `Add to .gitignore` opens a confirmation; it does not mutate immediately.
- Confirmation copy states that Diff Review will append exactly `/.diff-review/` to the repository-root `.gitignore` and preserve all existing bytes and rules.
- Final explicit actions are `Keep .gitignore unchanged` and `Append ignore rule`.
- Busy copy is `Appending one ignore rule…`; retries use `Try append again`.
- Unconfirmed or ambiguous outcomes never claim success, replacement, or rollback. Export can continue independently.

### Export Progress, Failure, and Publication Integrity

Progress uses one shared spinner, `role="status"`, and exact stage copy:

- `Preparing accepted revision {revision}…`
- `Validating export pair…`
- `Publishing export pair…`

The body MUST state that `review.json` and `review.md` become available only after both pass validation and publication checks. Progress never says one file succeeded or shows a partial receipt.

Failure uses `Export was not published` or `Export needs recovery`, states that no success receipt is available, and offers `Try export again` plus `Return to review`. A previous confirmed receipt may remain visible in a dashed, explicitly labeled `Previous confirmed export` block with the statement: `This last confirmed pair remains available; the later export attempt was not published.` It MUST NOT be styled as success for the failed attempt.

### Receipt

A success receipt appears only after both files are validated and published together. It contains:

- heading `Review export complete`;
- statement `Both files were published together from accepted revision {revision}.`;
- accepted draft revision;
- exported-at timestamp using `<time datetime>`;
- drift value and, when acknowledged, pinned/current identity details;
- each repository-relative path (`review.json`, `review.md` under the export directory as returned by the contract);
- algorithm and full SHA-256 hash;
- byte count for each file.

Receipt paths stay repository-relative; the browser MUST NOT expose or invent an absolute filesystem path. Actions remain `Copy all receipt details` and `Reveal export directory`; acknowledged drift adds `Copy acknowledged identities`. Copy/reveal success uses status semantics. Reveal failure states: `Could not reveal the export directory. Copy the relative path and open it from the repository root.` and moves focus according to existing behavior.

## Accessibility Contract

### Semantics and Names

- Preserve existing landmarks, heading relationships, disclosure buttons, tablist/tab/tabpanel semantics, native buttons/fields, `aria-expanded`, `aria-controls`, `aria-selected`, `aria-describedby`, `aria-labelledby`, `inert`, `aria-hidden`, status/alert roles, and focus restoration.

- Status SVGs and spinners are decorative and hidden from the accessibility tree. Visible labels carry meaning.
- Base/Head endpoint labels remain visible. Do not duplicate them through redundant hidden text when the containing context already has an accessible label.
- Badge counts are labeled `Open {N}` and `Resolved {N}`, not announced as ambiguous bare numbers.
- Selected comment presentation adds visible `Selected` text. If announced, use a non-interactive status description; do not make the entire article a button.
- Composer validation is adjacent and connected to the textarea; existing alert semantics remain.
- Accepted-comment heading retains the existing focus target and `{path} · Base|Head · line {N}` identity.

### Keyboard and Focus

- Every operable element retains the existing opaque 2px focus-visible outline with 2px offset. It is outermost and unclipped.
- Selected, hover, pressed, lifecycle, destructive, and busy treatments never remove or cover focus.
- Existing Alt/Option+Enter comment activation, F7/Shift+F7 change navigation, file shortcuts, `?` help, disclosure Enter/Space behavior, Summary tab arrow behavior, Escape confirmations/drawers, and Monaco commands remain unchanged.
- Local icons, rails, notices, badges, file groups, and comment articles do not create new tab stops.
- Busy actions retain focus where current behavior does and announce progress without moving focus to a spinner.

### Contrast and Non-Color Meaning

- Normal text and control labels target 4.5:1 against actual composited surfaces.
- Meaningful icons, input/control boundaries, selected rails, status edges, and focus rings target 3:1 against adjacent composites.
- Error/warning/info/success/pending/disabled/open/resolved, Base/Head, selected/focused, and stale/unavailable meaning always includes text/icon/structure beyond color.
- No whole card, resolved row, disabled control, or error body communicates state through reduced opacity alone.
- Focus, selected-comment rail, lifecycle badge, anchor warning, destructive button, and Monaco anchor rail remain distinguishable when they overlap.

### Forced Colors Compatibility

Phase 08 owns final forced-colors proof. Phase 07 MUST keep structural cues that survive palette override:

- Explicit 1px boundaries, 2px focus outlines, 3px selected/status rails, visible labels, and SVG geometry remain in the DOM.
- Ordinary components use system colors under the inherited fallback and MUST NOT set `forced-color-adjust: none`.
- Disabled maps to `GrayText`; focus/selected maps to `Highlight`; buttons retain `ButtonBorder`/`ButtonText`; links retain `LinkText`.
- Background tint and shadow loss MUST NOT erase status, selection, lifecycle, or hierarchy.

### Motion

The pending spinner is the only phase-owned animation. `prefers-reduced-motion: reduce` stops it; progressive text, icon geometry, and live/status announcements preserve meaning. No smooth scroll, shimmer, pulse, card transition, or decorative animation is introduced.
