<objective>
Collapse the two competing paint authorities on the hidden-region band down to one, and re-home the two canonical tokens that collapse strands.

Purpose: Monaco already paints the collapsed-region band from the `unchangedRegionBackground`, `unchangedRegionForeground`, and `unchangedRegionShadow` keys that the theme supplies, and `styles.css` re-paints the same pixels a different colour. Two authorities on one pixel is exactly how this rule drifted from the theme in the first place. The complication is that deleting the duplicate orphans `--surface-gap`, whose only consumer is that rule, and the phase also inherits `--diff-hunk-background`, which survives the drift gate solely because a prototype references it and has no production consumer at all.
Output: the duplicate band rule is gone; the collapsed-context edge controls become the production consumers of `--surface-gap` at rest and `--diff-hunk-background` when strengthened; the link-hover override retires in favour of the theme key plan 10-01 added; a real browser proves each surface against canonical token bytes.

Out of scope: the hunk-boundary decorations and the side-label geometry, both of which also touch `styles.css` and are sequenced after this plan to keep one owner per wave. No theme-key change — the key this plan relies on landed in plan 10-01. No change to the hidden-region density values or to Monaco's native control copy.
</objective>

All three edits below land in one commit. Between the deletion and the re-homing the drift gate is red with a no-consumer report for `--surface-gap`; that window must not survive the task, and it must not be closed by re-adding the deleted rule.

**Delete the duplicate band rule.** Remove the whole rule that targets the centre element of the hidden-lines widget inside the Monaco override block — the one setting a background, a shadow reset, and a colour. Monaco's own diff stylesheet already paints that element from the `unchangedRegionBackground`, `unchangedRegionForeground`, and `unchangedRegionShadow` custom properties, all three of which the theme supplies, with the shadow deliberately set to the unpainted sentinel. Every declaration in the Cumpa rule is therefore either a duplicate or a contradiction of what the theme already says, and the contradiction is what made the shipped band render a different colour than the approved contract specifies.

Do not resolve this the other way by re-pointing the theme key at `--surface-gap`. The approved theme table binds the band to `--surface-panel`, and changing it would additionally force an edit to the exhaustive theme-key test for no contract-sanctioned reason.

**Re-home `--surface-gap` onto the edge controls at rest.** The rule that currently sets only a border colour on the top and bottom elements of the hidden-lines widget becomes the collapsed-context strip's rest state: give it `background-color: var(--surface-gap)` and change its border colour from `--border-default` to `--border-gap`. This is the token's documented role — the Phase 08 contract names it the collapsed-context strip, and the mockup's gap rule pairs exactly this surface with exactly this border. It also separates the two authorities by element instead of stacking them on one pixel: Monaco owns the band, Cumpa owns the two edge affordances Monaco leaves unpainted. `--border-default` keeps many other consumers, so this swap orphans nothing.

**Re-home `--diff-hunk-background` onto the strengthened edge state.** The combined hover rule currently paints six selector arms with `--surface-panel`. Split it. The four edge arms — hovered top, hovered bottom, dragging top, dragging bottom — become their own rule using `background-color: var(--diff-hunk-background)` with the hunk foreground unchanged. Two things make this the right home rather than a convenience. First, once the band itself is `--surface-panel`, painting a hovered edge control `--surface-panel` is feedback the user cannot see; the hunk surface is the next step up in the same non-accent family and makes the affordance strengthen exactly as the interaction contract allows. Second, this is the token's only route to a production consumer: it is currently kept alive solely by a prototype that the gate happens to glob, which is the deferral Phase 08 recorded and this phase owns.

Retire the link-hover arm. Drop the arm targeting the hovered link's codicon inside the centre element from the rule entirely. Monaco paints that element with its own declaration marked important, so the Cumpa colour never applied; plan 10-01 supplied the theme variable Monaco actually reads, which makes the override both dead and redundant. Its background declaration is equally moot now that the band and that background are the same colour.

Keep the breadcrumb-item hover arm. Move it to its own rule retaining `--surface-panel` and the hunk foreground. It is not one of the edge affordances, no theme key has been shown to own it, and changing it is outside this plan's contract.

Two placement constraints. Every rule you write or move stays inside the existing Monaco override block and ahead of the reduced-motion media query, because the gate requires the forced-colors repair to remain the single terminal media block positioned after reduced-motion. And do not introduce a box-shadow anywhere in these rules: the gate matches inset shadows against an allowlist keyed on exact selector and exact value strings, and none of these selectors is on it.

Leave the prototype file alone. Removing its reference is not required — the token now has a production consumer, and touching a prototype that two gate assertions parse adds risk for no contract benefit.
