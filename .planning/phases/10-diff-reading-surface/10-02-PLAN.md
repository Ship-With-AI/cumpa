<objective>
Make Monaco's own accessible name source-correct for exact patches, and drive the three responsive code densities the UI-SPEC defines through Monaco's public options rather than through CSS.

Purpose: the side-label row is `aria-hidden`, so Monaco's `ariaLabel` is the only place a screen-reader user learns which side is which inside the editor — and it currently hard-codes base and head even when the session is an exact patch, where the correct names are preimage and postimage. Separately, the UI-SPEC defines three code densities across the wide and mobile breakpoints; CSS applied to rendered code spans is prohibited because it desynchronizes Monaco's layout maths and therefore the line mapping the comment anchors depend on.
Output: the adapter exposes `setSideNames` and `setCodeDensity`, both implemented through `updateOptions`; `DiffWorkspace.vue` owns two `matchMedia` listeners with teardown and hands the already-computed side names to the adapter; unit and browser assertions pin all three densities and the exact-patch label.

Out of scope: no `styles.css` change — responsive code type is deliberately not a CSS concern in this phase, and the stylesheet belongs to plans 10-03 through 10-05. No shell-level responsive behaviour: the shell's own `1099/1439/767` breakpoints are Phase 11's and must not be touched or conflated with the diff-local `1650/760` pair.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository file path → Monaco accessible name | The reviewed path is repository-controlled and already interpolated into the section's accessible name |
| browser viewport state → Monaco layout options | Untrusted only in the sense that it is environment-driven; it selects among three fixed density constants |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04 | Spoofing | Monaco `ariaLabel` composed in `setSideNames` | mitigate | The two side names come from the closed `visibleSides` computed, which yields one of exactly two fixed pairs; no file path or user string is interpolated into Monaco's label, so a crafted path cannot forge a misleading side identity. |
| T-10-05 | Tampering | `setCodeDensity` payload | mitigate | The density argument is one of three named constants and the numbers are parsed from the canonical `:root`; no viewport-derived number reaches `updateOptions`, so a hostile layout cannot drive arbitrary editor options. |
| T-10-06 | Denial of service | `matchMedia` listeners in `DiffWorkspace.vue` | mitigate | Both listeners are acquired in `onMounted` and released in `onBeforeUnmount`; the acceptance criteria assert balanced add/remove counts so repeated navigation cannot accumulate handlers. |
| T-10-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install task exists in this phase; `10-RESEARCH.md` records the Package Legitimacy Audit as not applicable. |

ASVS L1 scope for this plan is V5. No untrusted string reaches a DOM sink; the accessible name is built from a closed set of constants and handed to Monaco's option validator. No high-severity finding expected.
</threat_model>
