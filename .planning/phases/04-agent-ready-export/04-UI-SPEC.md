# Phase 4 — UI Design Contract

> Visual and interaction contract for explicitly publishing one accepted review revision as an agent-ready export. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Contract Status and Sources

This contract is prescriptive for Phase 4 planning. It implements `EXP-01`–`EXP-08`, `SAFE-04`, and locked Phase 4 decisions D-01–D-18 without reopening them. The planner and executor must also preserve the Phase 3 Review-panel, revision-conflict, corrupt/unsupported-draft, selector-drift, and comment-actionability contracts.

**Implementation baseline:** Phases 1–3 are unimplemented planning contracts as of 2026-07-11. Treat their plans as required upstream interfaces, not evidence of existing source. At implementation time, reconcile actual component and API names; extend the single canonical Review panel and draft state owner rather than creating parallel UI state.

**Inherited invariants:**

- The open review remains pinned to its original full base, head, and merge-base object identities. Export never refreshes, rebases, or substitutes current selector targets.
- The server-side accepted whole-draft revision is authoritative. Browser-local projected state and unsaved buffers are never export input.
- Accepted comments retain exact repository-relative path, side, line, blob, selected text, nearby context, and context-hash identity.
- Open + verified comments are actionable. Open + stale/orphaned comments are non-actionable and need reviewer attention. Resolved comments are non-actionable regardless of anchor status.
- Export, receipt, and ignore-status UI expose only safe repository-relative paths. Absolute filesystem paths never appear or reach clipboard text.
- Export creates only the pair beneath `.diff-review/` and, through a separate explicit consent action, may append exactly `/.diff-review/` to the repository-root `.gitignore`. It never applies, stages, commits, pushes, edits source, executes repository code, or offers source-control actions.
- A receipt exists only after the server confirms both published files as one validated pair. The receipt is UI/API state, not a third file in the export directory.

**Aesthetic direction:** continue the warm, compact, editorial code-review workbench established by the Phase 3 contract. The diff remains the dominant plane. Export is a deliberate completion workflow within the Review panel, not a celebratory publishing dashboard and not a generic file-save dialog.

## Review Panel Placement and Information Architecture

Extend the existing 360px Phase 3 Review panel; do not create a separate export page or replace the diff. Add one persistent **Export** section after Summary, Open comments, and Resolved comments. The panel hierarchy is:

1. Review header and canonical counts.
2. Summary.
3. Open comments grouped by exact canonical path.
4. Resolved comments disclosure.
5. Export section.

The Export section header contains `Export`, a quiet state label (`Ready`, `Needs acknowledgement`, `Exporting`, `Exported`, `Failed`, or `Unavailable`), and a disclosure control. It is expanded by default when the user has not yet exported this accepted revision; after a successful receipt it remains expanded. Closing the Review panel, changing active files, resizing, or collapsing Export preserves export status and any drift acknowledgement UI, but never continues a user action implicitly.

At rest, show a compact export-readiness summary derived from the canonical accepted revision:

- `Accepted revision {revision}`.
- `{N} open actionable` — open comments with verified anchors.
- `{N} need reviewer attention` — open stale or orphaned comments.
- `{N} resolved` — all resolved comments.
- `Summary included` or `No summary provided`.
- Ignore status: `/.diff-review/ is ignored` or `/.diff-review/ is not ignored`.

Counts are explanatory only and cannot select a subset. Export always includes the entire accepted revision. Never label the total comment count as the number of tasks.

The primary CTA is `Export review`. It is a button, never a toggle, autosave, panel-close side effect, keyboard shortcut, or background process. One activation initiates preflight against the displayed expected revision. Re-export uses the same explicit CTA labeled `Export review again`; it atomically replaces only the stable pair for the same pinned comparison after all checks succeed.

Supporting copy immediately below the CTA is exact:

> Creates `review.json` and `review.md` together from accepted revision {revision}. This does not apply, stage, commit, or push changes.

No source-control menu, status, branch switch, apply action, commit action, or push action appears in Export or the receipt.

## Explicit Export Interaction Contract

### Eligibility

`Export review` is enabled only when:

- a canonical current-schema draft is loaded with a known accepted revision;
- no whole-draft mutation is pending;
- no unresolved revision conflict is blocking canonical certainty;
- no export request is pending; and
- the server has not classified the draft as corrupt, schema-invalid, or newer-unsupported.

Unsaved local summary/comment/add buffers do not silently enter export. When any exist, keep the CTA enabled because the accepted canonical revision remains exportable, but place a warning immediately above it:

> Unsaved text in this tab is not included. Export uses accepted revision {revision}.

This warning has `Review unsaved text` as a neutral navigation action and does not offer `Include`, `Save all`, force-save, or automatic mutation. The user may still explicitly export the accepted revision.

### Initiation sequence

1. User activates `Export review` or `Export review again`.
2. Disable only duplicate export initiation while preflight runs; keep navigation, reading, copy, disclosures, and non-conflicting local editing available. Announce `Checking accepted revision for export.`
3. Server validates the expected accepted revision, draft readability, and current selector-drift observation.
4. If there is no drift, immediately start the pair-level export operation.
5. If drift exists, stop before generation/publication and present the required acknowledgement flow below.
6. A receipt replaces progress only after the server verifies complete pair publication and re-reads the final bytes/hashes.

Browser inputs contain only expected revision and an opaque server-issued drift acknowledgement token when required. The browser never supplies repository, ref, OID, export directory, filename, path, schema, hash, or content authority.

### Zero-actionable and empty-summary states

Zero actionable comments is valid and must not disable export. Show:

- Heading: `No open actionable requests`.
- Body: `The export will still include the accepted review, full comment history in JSON, and agent verification instructions.`

If the summary is empty, show `No summary provided`; do not treat it as validation failure and do not synthesize one. If there are no comments and no summary, use:

- Heading: `No review requests yet`.
- Body: `You can still export the accepted empty review record, or add a summary or comment first.`

The actions are `Export review` and neutral `Return to review`. Never say `Nothing to export`.

## Revision Conflict Contract

Export captures one accepted whole-draft revision. If the draft revision changes after the panel's expected revision or before publication, generation must not publish and the UI enters a conflict state in the Export section:

- Heading: `Review changed before export`.
- Body: `Accepted revision {expectedRevision} is no longer current. Nothing from this export attempt was published.`
- Metadata: `Latest revision {actualRevision}`.
- Primary recovery action: `Reload latest` (neutral/secondary, not accent).
- Supporting copy: `Reloading adopts the latest accepted review. It does not export automatically.`

`Reload latest` must use the inherited Phase 3 conflict behavior: adopt the latest canonical draft while preserving every unsaved local buffer. After reload, the Export section returns to `Ready` and requires a new explicit `Export review` activation. It never auto-retries, merges, force-exports the older revision, or offers `Export mine`.

If the canonical revision changes during generation, use the same conflict surface. Do not show a receipt, a success badge, either new path as complete, or a partial-success message.

## Corrupt and Read-Only Draft Contract

Phase 3 corrupt/schema-invalid and newer-unsupported states replace mutable Review content with their existing read-only recovery/upgrade surfaces. Phase 4 must not introduce an export escape hatch:

- No enabled `Export review`, `Export anyway`, raw-file export, downgrade, or best-effort preview action.
- Show a quiet disabled Export summary only when the inherited recovery layout has room: label `Export unavailable`; body `A readable accepted draft is required before export.`
- Malformed/current-schema-invalid recovery retains `Reveal draft file`, `Copy draft path`, and inherited verified backup/start-new recovery only.
- Newer-unsupported state retains only `Reveal draft file` and `Copy draft path`; it never gains reset, conversion, or export.
- The existing draft bytes remain unchanged and read only. Export classification must never replace the state with an empty draft.

If readability changes or corruption is discovered during export preflight, stop before publication and focus the inherited read-only recovery heading. Assertive announcement: `Export stopped because the accepted draft could not be read safely. No new export pair was published.`

## Selector Drift Warning and Acknowledgement

Selector drift never invalidates or refreshes the pinned comparison. The inherited persistent drift notice below the identity header remains visible. Export adds acknowledgement only when the user explicitly initiates export.

### Acknowledgement surface

When either selected source moved or became unavailable, preflight returns an opaque observation and no files are generated or published. Expand `DriftExportAcknowledgement` directly above the export CTA:

- Heading: `Confirm export of pinned review`.
- Warning: `Selected sources changed after this review opened. Export will use the original pinned comparison, not the current source targets.`
- One row per Base and Head source showing source label/type, `Pinned at` full untruncated OID, and either `Now at` full untruncated OID or `Now unavailable` with bounded reason.
- Required checkbox label: `I understand this export remains pinned to the original commits and records the selector drift.`
- Safe action: `Cancel export`.
- Accent action: `Export pinned review`, disabled until the checkbox is checked.

Checking the box is local consent only. Activating `Export pinned review` submits the latest opaque observation token. Merely checking, collapsing the section, pressing Enter elsewhere, or navigating files never publishes.

There is no `Refresh`, `Update comparison`, `Use current commits`, `Move anchors`, `Reattach`, or silent refresh action. The inherited `Launch new comparison` guidance may remain outside Export, but never substitutes current identities into this export.

### Observation changes before commit

If drift changes after acknowledgement but before publication, invalidate the old acknowledgement, publish nothing, and replace the surface with:

- Heading: `Selected sources changed again`.
- Body: `The previous acknowledgement is out of date. Review the latest source identities before exporting the same pinned comparison.`
- Updated full launch/current identity rows.
- Unchecked acknowledgement checkbox.
- Actions: `Cancel export` and disabled-until-checked `Export pinned review`.

Announce the change assertively once. Never preserve a checked box across a changed observation and never refresh the pinned comparison.

### Receipt drift state

The receipt states exactly one of:

- `Drift: none observed` when launch/current identities remain unchanged.
- `Drift: acknowledged for this export` when moved/unavailable state was explicitly acknowledged.

For acknowledged drift, include an expandable `View acknowledged identities` detail with full pinned/current values. It remains informational and offers copy only; no refresh or navigation mutation.

## `.diff-review/` Ignore and Explicit Gitignore Consent

Ignore inspection is informational and independent of export correctness. `.diff-review/` remains excluded from the reviewed change set whether ignored or not.

### Ignored state

Show a neutral status row:

- Label: `Export directory ignored`.
- Body: “Git already ignores `/.diff-review/`.”
- No append action.

### Unignored state

Show a persistent warning in the Export section and, after success, in the receipt:

- Heading: `Export directory is not ignored`.
- Body: “Export can continue. Diff Review always excludes `.diff-review/` from this review, but Git may show the generated files as untracked.”
- Separate secondary action: `Add to .gitignore`.
- Neutral action: `Keep .gitignore unchanged`.

Declining or ignoring the offer never blocks or cancels export. It records only session-level presentation state; it does not enter canonical JSON and must not suppress the persistent unignored warning.

### Append-only consent

The first `Add to .gitignore` activation performs no mutation. It expands an inline `UiConfirmRow`:

- Heading: `Add export directory to .gitignore?`
- Body: “Diff Review will append exactly `/.diff-review/` to the repository-root `.gitignore`. Existing bytes and rules will be preserved.”
- Safe action first: `Keep .gitignore unchanged`.
- Consequential action second: `Append ignore rule`.

Only the second explicit activation invokes the fixed server capability. The request accepts no path, pattern, text, repository, or replacement-content input. Pending copy: `Appending one ignore rule…`. Disable duplicate append controls but do not block an unrelated export already in progress.

On success, announce “Added `/.diff-review/` to `.gitignore`.” and replace the warning with the ignored state after effective ignore status is rechecked. Do not claim a rewrite, stage, or commit.

On failure, retain the warning and show:

- Heading: `.gitignore was not changed`.
- Body: “The ignore rule could not be appended safely. Export can continue; existing `.gitignore` content was not replaced.”
- Actions: `Try append again` and `Keep .gitignore unchanged`.

If `.gitignore` is a symlink, non-regular file, read-only, changes concurrently, or safe append verification fails, use this same non-destructive failure contract with a bounded safe reason. Never offer overwrite, chmod, replacement, merge, editor launch, `git add`, or commit.

## Publication Progress Contract

Progress is one pair-level operation. Never show independent JSON/Markdown checkmarks, `1 of 2 complete`, percentages based on file count, or a path before complete publication is confirmed.

Use one inline status surface with spinner and exactly one current phrase:

1. `Preparing accepted revision {revision}…`
2. `Validating export pair…`
3. `Publishing export pair…`

Persistent supporting copy throughout:

> `review.json` and `review.md` become available only after both pass validation and publication checks.

The originating CTA is disabled and labeled `Exporting…`. Navigation, reading, copy, disclosure, and local unsaved editors remain usable. Do not optimistically change canonical review state, clear local buffers, collapse warnings, or disable the whole workspace. There is no cancel action once server publication begins; closing the panel does not imply cancellation. Reopening restores the same server-owned pending status.

Progress uses `role="status"` with polite updates and one announcement per stage transition. Reduced-motion users receive the same text without spinner rotation. Do not estimate time or claim durability before the receipt response.

## Publication Failure and Recovery

Any generation, validation, hashing, snapshot revalidation, filesystem, durability, rollback, or recovery failure that does not return a confirmed receipt uses one pair-level failure state:

- Heading: `Export was not published`.
- Body: `No new export pair was made available. Any previous complete export remains unchanged.`
- Bounded reason: a safe stage-specific explanation such as `The export pair could not be validated.`; never expose absolute paths, temp names, raw JSON, stack traces, or secrets.
- Actions: `Try export again` and `Return to review`.
- Supporting copy: `Retry starts a new complete export attempt from the current accepted revision.`

`Try export again` is always an explicit fresh action and reruns revision/drift preflight. It never resumes halfway, retries one file, or assumes the previous drift acknowledgement remains current.

If recovery cannot safely determine publication state, use the stronger heading `Export needs recovery` and body `Diff Review could not confirm a complete new export pair. No success receipt is available. Check terminal details, then try again after recovery.` Do not list either candidate as published. Any prior server-confirmed receipt may remain visible under `Previous confirmed export`, visually separated from the failed current attempt and never relabeled as current success.

Failure is an assertive `role="alert"` announced once. Focus the failure heading after a user-initiated export. No failure state may say `JSON exported`, `Markdown failed`, `partially exported`, `one file written`, or otherwise claim partial publication succeeded.

## Completion Receipt Contract

Show the receipt only for a server-confirmed, final, re-read complete pair. The success surface remains inside Export and has:

- Heading: `Review export complete`.
- Body: `Both files were published together from accepted revision {revision}.`
- `Accepted revision`: exact integer in monospace.
- `Exported at`: one UTC RFC 3339 timestamp used by both artifacts and receipt.
- `Drift`: `None observed` or `Acknowledged for this export`.
- `Comparison`: full pinned Base and Head OIDs in a disclosure; labels are supplementary only.
- Exactly two file rows in fixed order: `review.json`, then `review.md`.

Each file row contains:

1. full repository-relative POSIX path, e.g. `.diff-review/exports/<fullBaseOid>..<fullHeadOid>/review.json`;
2. full lowercase 64-character `sha256:<hash>` calculated from exact published bytes;
3. byte count when returned by the server;
4. `Copy path` button specific to that row.

Receipt actions below the rows:

- `Copy all receipt details` — copies accepted revision, timestamp, drift state, and both relative paths/hashes as plain text; no absolute path.
- `Reveal export directory` — invokes only the fixed active-comparison reveal capability; the browser supplies no path.
- `Export review again` — starts a new complete preflight and pair publication.

Path copy success announces `Copied relative path for {filename}.`; all-details success announces `Copied export receipt details.` The button label may temporarily become `Copied` for 2 seconds without changing layout. Clipboard failure shows adjacent `Could not copy. Select the value and copy it manually.` and exposes selectable full text. Reveal failure says `Could not reveal the export directory. Copy the relative path and open it from the repository root.`

If unignored, retain the warning “Export complete, but `/.diff-review/` is not ignored.” and the separate explicit `Add to .gitignore` flow. Receipt success must not imply Git tracking, staging, commit, push, delivery to an agent, or source modification.

## Actionability and Non-Actionability Contract

The readiness summary and receipt may report derived counts but must not create a second comment classification model.

| Comment state | Anchor status | Export classification | UI treatment |
|---------------|---------------|-----------------------|--------------|
| Open | Verified | Open actionable request | Included in actionable count; ordinary Phase 3 `Show comment`/Edit/Resolve/Delete semantics remain |
| Open | Stale | Needs reviewer attention; non-actionable | Warning count; never offered as an export task, relocation, refresh, or apply action |
| Open | Orphaned | Needs reviewer attention; non-actionable | Warning count; never offered as an export task, relocation, refresh, or apply action |
| Resolved | Any | Resolved history; non-actionable | Resolved count only in readable Markdown; retained fully in canonical JSON; no export action can reopen/apply it |

Export does not mutate any comment state. Stale/orphaned records remain visible through the inherited Review panel, retain allowed Phase 3 lifecycle actions, and remain non-actionable in export. Resolved comments never appear as requested work in Markdown. No UI offers `Mark actionable`, `Fix anchor`, `Apply`, `Send to agent`, selective export, or comment checkboxes.

When needs-attention count is nonzero, show this exact notice without blocking export:

- Heading: `{N} comments need reviewer attention`.
- Body: `Stale or unavailable anchors will be exported as non-actionable records. An applying agent is instructed not to guess or relocate them.`
- Neutral action: `Review comments`.

## Exact UI State Priority

Higher priority owns the Export surface; lower states may remain as non-interactive context only:

| Priority | State | Required presentation |
|----------|-------|-----------------------|
| 1 | Session/auth/fixed-authority failure | Inherited blocking session error; no export or reveal authority |
| 2 | Corrupt/schema-invalid/newer-unsupported draft | Inherited read-only recovery/upgrade surface; export unavailable |
| 3 | Revision conflict | `Review changed before export`; reload required; no publication/receipt |
| 4 | Drift acknowledgement required or stale | Full identity warning and unchecked explicit acknowledgement; no generation |
| 5 | Export publication/recovery failure | Pair-level failure; no current receipt or partial-success claim |
| 6 | Export pending | Pair-level progress; duplicate export disabled |
| 7 | Complete confirmed receipt | Receipt with revision/time/drift/paths/hashes and copy/reveal actions |
| 8 | Ready/zero-actionable/no-summary | Readiness summary and explicit CTA |

Ignore status is an independent slot. Unignored warning persists alongside priorities 4–8 and never blocks export. A gitignore append failure never replaces export success/failure state. Existing Phase 3 whole-draft mutation pending state disables export initiation; export pending does not convert local attempted text into canonical state.

- Resize preserves panel/disclosure state, drift checkbox only while its observation remains current, pending state, receipt, scroll position, and every upstream local edit buffer.

## Accessibility and Keyboard Contract

### Structure and naming

- Preserve inherited landmarks: `header` (`Pinned comparison`), `nav` (`Changed files`), `main` (`Diff review`), and `aside` (`Review`). Export is a labeled section within the Review aside.
- `Export` is an `h3` under the Review `h2`; drift, failure, and receipt headings follow a valid hierarchy.
- Every icon button has an accessible name and delayed tooltip. Tooltips are never the sole source of required identity or state.
- Status badges contain visible text. Color and icons never carry state alone.
- Checkbox label includes the complete drift consequence; it is not an unlabeled `Acknowledge` control.
- Hash and path text are selectable, use semantic labels, and are not placed only in pseudo-elements or tooltips.

### Focus behavior

- User-initiated export preflight keeps focus on the originating button until a new state is known.
- Drift required: move focus to `Confirm export of pinned review`; next Tab reaches full identity details, checkbox, `Cancel export`, then `Export pinned review`.
- Stale drift observation: focus `Selected sources changed again`; reset checkbox to unchecked.
- Revision conflict: focus `Review changed before export`; `Reload latest` is the next primary recovery target.
- Publication failure: focus `Export was not published`; Retry follows supporting reason.
- Success: focus `Review export complete`; do not auto-focus Reveal or copy controls.
- Gitignore confirmation focuses `Keep .gitignore unchanged`. Escape chooses the safe action and returns focus to `Add to .gitignore` without mutation.
- Copy feedback does not steal focus. Reveal failure focuses its inline error only after the user invoked Reveal.
- Closing the Review drawer while focus is inside returns focus to the `Review` trigger; reopening restores state, not stale DOM focus.

### Keyboard behavior

| Context | Keys | Behavior |
|---------|------|----------|
| `Export review` / `Export review again` | Enter or Space | Starts preflight exactly once |
| Drift checkbox | Space | Toggles acknowledgement for current observation only |
| `Export pinned review` | Enter or Space | Submits only when checkbox is checked; no implicit refresh |
| Disclosure | Enter or Space | Toggles details only; never starts export |
| Gitignore confirmation | Escape | Keeps `.gitignore` unchanged and returns focus |
| Any export error | Escape | Does not dismiss required warning, retry, reload, or mutate state |

No global keyboard shortcut starts export, appends `.gitignore`, reveals a directory, or retries publication.

### Live regions and announcements

Use one polite `role="status"` region for checking, stage progress, copy success, receipt success, and ignore-append success. Use assertive `role="alert"` once for revision conflict, stale drift acknowledgement, corrupt/read-only classification during export, publication failure, access failure, and ignore append failure. Do not announce unchanged selector polling, every spinner frame, every hash row, or repeated receipt re-render.

Required announcements:

- `Checking accepted revision for export.`
- `Selected sources changed. Confirm export of the pinned review.`
- `Selected sources changed again. Review the latest identities.`
- `Exporting accepted revision {revision}.`
- `Review export complete. Both files were published together.`
- `Export was not published. No new export pair is available.`
- `Copied relative path for {filename}.`
- `Added `/.diff-review/` to .gitignore.`

### Contrast, zoom, motion, and targets

- Normal text meets WCAG AA 4.5:1; large text, focus indicators, component boundaries, and state indicators meet 3:1.
- Every action is keyboard-operable with a visible focus style. Controls have at least 32×32px targets and sufficient spacing between safe and consequential actions.
- At 200% zoom, responsive layout activates before labels, paths, hashes, or actions clip or overlap.
- `prefers-reduced-motion` removes spinner rotation/transitions while status copy remains available.
- Screen readers receive one complete path/hash label per file, not character-by-character hash announcements caused by decorative spans.

## Meaningful Error and Recovery Matrix

| State | User-visible meaning | Recovery | Forbidden implication/action |
|-------|----------------------|----------|------------------------------|
| Revision conflict | Expected accepted revision changed; attempt published nothing | `Reload latest`, then explicit new export | force old revision, auto-retry, merge |
| Corrupt/schema-invalid | Canonical draft cannot be read safely and remains preserved | inherited reveal/copy/verified backup recovery | export anyway, empty fallback |
| Newer schema | Current app cannot understand draft and file remains unchanged | reveal/copy, upgrade Diff Review | downgrade/reset/export |
| Drift acknowledgement required | Current source targets differ, pinned review unchanged | inspect full identities, check acknowledgement, `Export pinned review` | refresh/substitute/move anchors |
| Drift acknowledgement stale | Observation changed after consent | inspect updated identities and acknowledge again | retain old consent |
| Unignored `.diff-review/` | Export works, generated files may appear untracked | optional explicit append or decline | automatic write/stage/commit |
| Append failed | `.gitignore` not safely changed | retry append or keep unchanged; export remains allowed | rewrite/overwrite/chmod |
| Publication failed | No confirmed new pair/receipt | fresh `Try export again` | partial-success claim |
| Reveal failed | Export remains successful; directory could not be opened | copy relative path and open from repository root | browser-selected path |
| Clipboard failed | Receipt remains selectable | manual selection/copy | hide full value |
| Zero actionable | Complete export remains meaningful | export or return to review | `Nothing to export` |

## Non-Goals and Prohibited UI

1. No automatic export on save, resolve, panel close, browser close, server shutdown, or selector polling.
2. No export subset, comment checkboxes, file selection, alternate output directory, renamed files, or browser-provided path.
3. No refresh/rebase/update-comparison flow. Selector drift is acknowledged and recorded; the pinned comparison never changes.
4. No anchor relocation, fuzzy matching, line-only authority, stale/orphan promotion, or resolved-comment application.
5. No applying-agent execution, direct agent delivery, issue creation, forge publication, clipboard agent instructions, or remote integration.
6. No source edits, apply, stage, add, commit, push, checkout, reset, branch creation, hook execution, repository-code execution, terminal command, or source-control action.
7. No automatic `.gitignore` modification, rewrite, rule normalization, sorting, newline conversion, duplicate cleanup, or broad pattern. Only explicit append of exactly `/.diff-review/` is offered.
8. No partial-publication UI, per-file success, intermediate path, candidate/backup name, temporary-generation progress, or receipt before verified complete publication.
9. No third artifact in the stable comparison directory; the UI receipt is not written beside `review.json` and `review.md`.
10. No success confetti, celebratory animation, progress percentage, duration estimate, or green state before complete confirmation.
11. No second draft/export authority, client-side canonical serializer, independently rendered Markdown, client-computed receipt hash, or cached actionability index.
12. No new design system, component registry, third-party block, icon package, modal framework, file picker, or toast queue.
