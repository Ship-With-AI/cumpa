# Phase 06 — UI Design Contract

> Visual and interaction contract for Phase 06: Monaco Diff Semantics. Generated by gsd-ui-researcher for planner, executor, checker, and auditor use.

---

## Contract Boundary

Phase 06 themes the existing read-only, side-by-side Monaco diff so its canvas, syntax, whole-line and intraline changes, gutters, hidden and empty regions, widgets, selection, active line, hover affordance, persistent comment anchor, and focus state compose with the Phase 05 dark semantic foundation.

The implementation MUST preserve the existing `PublicMonacoDiffAdapter`, immutable models, original/modified side ownership, line mapping, public Monaco APIs, paired view zones, hidden-region settings and reveal behavior, `renderSideBySide: true`, `renderSideBySideInlineBreakpoint: 0`, file-state restoration, accessibility labels, keyboard commands, comment lifecycle, persistence, and editor geometry. The implementation MUST register and select one typed, idempotent Monaco theme before `monaco.editor.createDiffEditor(...)`.

Detailed file-header, comment-card, notice, review-rail, and control adaptation belongs to Phase 07. Structural responsive changes, 400% zoom acceptance, forced-colors acceptance, and final composited WCAG proof belong to Phase 08. Phase 06 MUST leave those surfaces usable and MUST NOT claim those later requirements complete.

Locked decisions D-01 through D-08 in `06-CONTEXT.md` are authoritative.

### Requirement Mapping

| Requirement | Implementation-ready contract |
|-------------|-------------------------------|
| DIFF-01 | One typed Monaco theme consumes the Phase 05 semantic palette and is selected before editor construction. Canvas, code tokens, gutter, widgets, scrollbars, separators, selection, and diff regions cannot fall back to Monaco's default light or unrelated dark colors. |
| DIFF-02 | Whole-line additions/deletions use 15% semantic fills; intraline changes use 35% fills plus a semantic edge. Normal unchanged code stays on canvas, collapsed-context widgets use a bounded panel step, empty counterpart regions use a flat inset neutral, and hunk purple is reserved for context reveal controls/separators. |
| DIFF-03 | Base/deletion and Head/addition remain identifiable in grayscale through persistent `BASE`/`HEAD` labels, fixed left/right ownership, a continuous 2px change bar, and sparse literal `−`/`+` gutter signs. Hue is supporting information only. |
| DIFF-04 | Line numbers remain muted but legible; the active number becomes primary text and its line gains a 1px edge. Existing 32px comment affordance remains a distinct blue bordered button. All diff bars and signs render inside already allocated Monaco gutter lanes, with no code movement or gutter reflow. |
| DIFF-05 | State precedence uses separate visual channels: diff fill, selection fill and edge, active-line edge, comment-anchor rail, hover/button emphasis, and a two-pixel focused-pane perimeter. No interaction state replaces the addition/deletion layer with an opaque row fill. |

## Spacing Scale

All authored spacing remains on the inherited 4-point scale. Phase 06 MUST NOT alter Monaco's measured content, glyph-margin, line-number, scrollbar, sash, minimap, folding, or view-zone geometry merely to obtain a visual effect.

| Token | Value | Usage |
|-------|-------|-------|
| `space-xs` | 4px | Compact icon/text gaps and context-widget inset |
| `space-sm` | 8px | Related controls, side-label inset rhythm, gutter-action offset |
| `space-md` | 16px | Side-label horizontal padding, workspace help inset, view-zone card margin |
| `space-lg` | 24px | Existing separated review groups only |
| `space-xl` | 32px | Existing shell spacing and the existing comment-affordance target size |
| `space-2xl` | 48px | Existing major shell separation only |
| `space-3xl` | 64px | Existing workspace/header geometry only; not a Monaco interior spacing value |

**Fixed density contracts**

- Preserve the existing 32px side-label row and `grid-template-rows: 32px minmax(0, 1fr) auto`.
- Preserve the existing comment action at 32px × 32px, 4px padding, 8px edge offset, and at least 8px separation from another target.
- Preserve Monaco's current line height, character width, line-number allocation, glyph margin, sash position, scroll dimensions, and paired-zone placement.
- New signs and rails are painted into existing decoration lanes. They MUST NOT add padding, width, margin, view zones, injected text, or content widgets.

**Non-spacing exceptions:** 1px separators/selection edge/active-line edge, 2px focus perimeter/change bar/composer border, and 3px comment-anchor rail. Existing 4px/6px/8px radii remain shape values, not spacing exceptions.

## Typography

Exactly four sizes and two weights are allowed across the inherited workspace and Phase 06 additions.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Metadata / gutter sign / `BASE`–`HEAD` label | 12px | 400 or 600 | 16px |
| Body / control / code / line number | 14px | 400 | 20px |
| Section heading | 16px | 600 | 24px |
| Page or state heading | 20px | 600 | 28px |

### Typography Rules

- Allowed weights are regular `400` and semibold `600` only. No `500`, `700`, synthetic bold, or italic syntax treatment.
- Monaco code and line numbers remain 14px/20px in the existing local monospace stack. Do not change Monaco font metrics if the rendered defaults already satisfy these values; geometry preservation wins over a redundant option write.
- Syntax hierarchy is carried by hue and token category, never font-size, font-weight, italics, underlines, or altered letter spacing. The sole underline exception is the invalid-token error cue.
- `BASE` and `HEAD` remain 12px/16px semibold uppercase labels with no more than `0.04em` letter spacing.
- Literal diff signs use 12px/16px semibold monospace so `−` and `+` have stable visual width.
- The active line number changes from muted to primary foreground; it does not resize or alter line-number alignment.

### Direct Semantic-Token Contract

- `src/web/styles.css :root` remains the sole CSS semantic-token root. Phase 06 MUST add only the five approved syntax roles listed below to that root; it MUST NOT add aliases, a Monaco-only token root, component-named color variables, or a second palette block.
- Existing Phase 05 roles remain canonical wherever they pass. The five new syntax roles are a narrow accessibility extension approved by this contract because the former interactive/status colors fail over locked intraline composites.

| Canonical root role | Exact value | Typed Monaco use |
|---------------------|-------------|------------------|
| `--syntax-keyword-foreground` | `#D2A8FF` | `keyword*`, `storage`, `control`, `tag` |
| `--syntax-string-foreground` | `#A5D6FF` | `string*`, `attribute.name` |
| `--syntax-number-foreground` | `#F2CC60` | numeric/language/character constants |
| `--syntax-type-foreground` | `#79C0FF` | `type*`, class/interface/namespace |
| `--syntax-invalid-foreground` | `#FFA198` | `invalid*` plus underline |

- The typed `IStandaloneThemeData.rules` entries MUST duplicate these five root bytes exactly. Existing mappings likewise remain byte-identical: default/callable `--text-primary` → `E6EDF3`, comment/operator `--text-secondary` → `B1BAC4`, and selected text `--text-on-emphasis` → `#FFFFFF`.
- Alpha values remain the exact hexadecimal equivalents of Phase 05 diff/selection variables. If runtime CSS-token extraction is used, a missing or invalid token MUST fail explicitly before editor construction; no silent `vs-dark` fallback is allowed. If typed literals are required by Monaco, a contract test MUST assert byte-for-byte parity with every referenced root role so the typed theme cannot become a parallel palette.
- Raw colors may appear only in root semantic declarations and the one typed Monaco mapping. Component CSS consumes root roles.

### Monaco Theme Registration

Use one stable identifier such as `diff-review-dark`. Theme data MUST satisfy `monaco.editor.IStandaloneThemeData`, use `base: 'vs-dark'`, `inherit: true`, and be defined and selected before the first `createDiffEditor` call. Repeated adapter construction MUST redefine/select the same identical theme safely; it must not append style blocks, allocate per-editor theme names, flash the base theme, or depend on network state.

The adapter continues to create the same diff editor once. Theme registration is a visual prerequisite, not a lifecycle rewrite.

## Monaco Canvas and Side Ownership

1. `BASE` remains the left/original/deletion-owned pane. `HEAD` remains the right/modified/addition-owned pane.
2. Both side labels use the same panel background, typography, width, and padding. Their exact uppercase text and order remain unchanged.
3. The editor canvas uses `surface-canvas`; its gutter uses `surface-inset`; the center divider uses `border-default`. No pane receives a red or green canvas tint.
4. The Monaco host retains `min-width: 640px`, the same height behavior, the same 50/50 split, and the same sash. No theme rule can change code origin, pane width, or line wrapping.
5. The existing accessible label `Immutable base and head side-by-side diff` and outer path-specific section label remain unchanged. Visible Base/Head labels reinforce rather than replace those names.
6. Scrollbars and all visible editor widgets stay dark from first editor paint. No browser-default or base-theme flash is acceptable.

## Diff Layer Language

### Whole-Line and Intraline Changes

- Whole-line additions use `#2EA04326`; whole-line deletions use `#F8514926`. These restrained alpha layers keep syntax and selection readable.
- Intraline additions use `#2EA04359` and a `#3FB950` edge; intraline deletions use `#F8514959` and a `#F85149` edge. Exact changed spans must lead the visual hierarchy.
- Monaco's existing line and character mapping remains authoritative. Phase 06 styles the ranges Monaco computes; it MUST NOT recompute textual diffs or alter `getLineChanges()` semantics.
- No line layer may set code foreground, opacity, font weight, or text decoration. Deleted source remains readable and is not struck through in the side-by-side editor.

### Continuous Change Bars and Sparse Signs

Set Monaco `renderIndicators: false` to suppress its repeated per-row indicator icons while retaining Monaco's built-in line/character decorations. Replace only that repeated visual channel with phase-owned model decorations derived from the same public `getLineChanges()` result already available after diff update.

For each contiguous original/deletion or modified/addition range:

- Paint one continuous 2px bar through the allocated line-decoration/glyph lane for the full valid line range: red for Base/deletion, green for Head/addition.
- For a 1–3 line range, paint one literal sign at the first changed line only.
- For a range of 4 or more lines, paint literal signs at the first and last changed lines only.
- Use U+2212 `−` for Base/deletion and ASCII `+` for Head/addition. Never substitute a hyphen, color-only dot, repeated sign on every row, or icon-library glyph.
- A sign is a non-interactive decoration, 12px/16px semibold monospace, centered in an already allocated gutter lane. It creates no ARIA role, pointer target, tab stop, tooltip, or injected model text.
- The bar and signs must survive selection, active line, anchor, hover, and focused-pane states because none of those states paints over the gutter.
- On an empty counterpart, paint no false sign on a nonexistent model line. The populated side carries its correct signed cue; the opposite recessed empty region and persistent Base/Head label complete the relationship.

The static green addition `+` MUST remain visually distinct from the blue `Add comment…` button: the diff sign is small, borderless, surface-less, fixed in the gutter, and non-interactive; the comment action is a 32px bordered button with an accessible action label and tooltip.

### Hidden, Unchanged, Hunk, and Empty Regions

| Region | Visual contract | Interaction contract |
|--------|-----------------|----------------------|
| Normal unchanged code | `#0D1117`, no special fill or texture | Existing read-only navigation |
| Collapsed unchanged region | `#161B22` bounded by 1px `#30363D`; purple only on reveal glyph/text/separator | Preserve `contextLineCount: 3`, `minimumLineCount: 8`, `revealLineCount: 10`, Monaco labels, controls, and bounded/all reveal behavior |
| Revealed context | Returns to normal canvas; a quiet purple 1px hunk separator may mark the reveal boundary | Preserve scroll position and line mapping |
| Empty counterpart region | Flat `#010409` recessed neutral with `#30363D` boundary; no visible diagonal contrast, stripe, hatch, gradient, or illustration | Non-interactive; never mistaken for loading or an error |
| Entirely empty side | Same inset neutral under persistent Base/Head label | Preserve the immutable empty model and opposite-side content geometry |
| Composer spacer zone | Neutral canvas/inset support surface, `aria-hidden="true"`; never styled as an empty diff | Preserve exact paired height and suppression of mouse action |

Hunk purple is not a changed-line fill and does not replace addition/deletion red or green.

## Overlap Precedence

Visual layers compose in the following back-to-front order. Each layer uses a different channel; later layers MUST NOT clear or replace earlier semantic information.

| Order | State | Channel | Forbidden treatment |
|-------|-------|---------|---------------------|
| 1 | Canvas and syntax | Neutral canvas plus token foreground | Pane-wide red/green tint |
| 2 | Whole-line diff | 15% red/green row fill | Opaque fill or foreground replacement |
| 3 | Intraline diff | 35% red/green span fill plus 1px semantic edge | Bold/italic text or unreadable opaque block |
| 4 | Text selection | 35% focused / 25% inactive blue fill, crisp 1px blue inset edge, and phase-owned white foreground class applied through public inline decorations | Clearing diff classes, token-specific recoloring, injected content, private selection DOM hooks, or any geometric override |
| 5 | Active line | Transparent row with 1px `border-strong` perimeter; active number becomes primary | Another row fill |
| 6 | Persistent comment anchor | 3px blue inset rail on `.monaco-anchor-line` | Blue full-row background |
| 7 | Hover/current anchor affordance | Existing 32px blue bordered comment button appears/emphasizes | Hover row fill, layout shift, gutter width change |
| 8 | Keyboard focus | 2px focus perimeter around the focused Base or Head editor pane | Removing any lower cue, clipping, or relying on caret alone |

### Selection

- Focused selection maps to `#388BFD59`; inactive selection maps to `#388BFD40`.
- Add a 1px inset edge in `#58A6FF` to Monaco 0.55.1's `.selected-text` overlays without changing their bounds. Edge segments may join across wrapped visual fragments; no outline may enlarge scroll dimensions.
- Set `editor.selectionForeground` to `#FFFFFF` for Monaco's high-contrast path. For the regular `vs-dark` path, the selected model ranges MUST receive `monaco-selection-contrast-foreground` through `createDecorationsCollection()` with `inlineClassNameAffectsLetterSpacing: false`; that phase-owned class alone sets `color: var(--text-on-emphasis) !important`. The `.selected-text` edge rule MUST NOT set foreground, and diff line/intraline decorations remain foreground-free. Gutter bar/sign, active-line edge, comment rail, and focused-pane perimeter remain visible.
- Selection cannot become the current-comment indicator; the anchor rail owns that meaning.

### Active Line

- `editor.lineHighlightBackground` is transparent.
- `editor.lineHighlightBorder` is a 1px `#484F58` full-width edge.
- The active line number is `#E6EDF3`; other numbers remain `#8B949E`.
- Moving the caret changes only the line edge, active number, and existing comment affordance target. It does not recolor the row or move code.

### Hover Affordance

- Pointer hover over a valid visible line and keyboard cursor movement continue to use the existing adapter target calculation.
- Hover reveals/emphasizes the existing `.diff-workspace__gutter-action`; no code-row background is added.
- Exact button glyph remains `+`; exact accessible name is `Add comment to {base|head} line {N}`; exact title is `Add comment to {base|head} line {N} · Option+Enter`.
- The action remains blue, bordered, and surface-backed so it cannot be confused with a static green addition marker.
- Hover-only discovery is prohibited: cursor/focus movement and `Option+Enter` remain the keyboard path.

### Persistent Comment Anchor

- `.monaco-anchor-line` receives a 3px inset `interactive-accent` rail at the code-side start edge and no added row fill.
- The rail persists while a composer or accepted comment owns that anchor and aligns visually with the existing 2px composer border.
- The rail cannot shift text, affect line height, occupy a new gutter lane, or replace the side/line label rendered in the view zone.
- The counterpart spacer never receives the anchor rail.

### Focus

- Add stable phase-owned Base/Head classes through the public editor container DOM nodes if a selector hook is needed. Do not depend on private Monaco services.
- A pane containing focus shows a 2px `#58A6FF` perimeter on the visual inner edge of its existing bounds so `.diff-workspace` overflow cannot clip it. The perimeter is the outermost visual channel, uses a non-layout pseudo-element or inset outline, and has `pointer-events: none`.
- Only the currently focused Base or Head pane receives the editor perimeter. Existing buttons and composer fields retain the Phase 05 2px focus-visible outline with 2px offset.
- Focus remains visible when the focused line is added/deleted, selected, active, and anchored. The caret is not the only focus cue.
- No new focus trap, tab stop, command, focus restoration rule, or focus-side state is introduced.
