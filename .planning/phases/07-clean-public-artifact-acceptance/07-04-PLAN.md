<objective>
Prove ACC-04 for a public installation path across the three real voluntary-support states — live unverified, dismissed, and genuinely verified through the product's Restore flow — and make the unreachable-prerequisite outcome an explicit blocked row rather than a silent pass or a substituted observation.

Purpose: The existing support coverage in the acceptance suites proves only unavailable-and-dismissed behaviour behind a non-loopback fetch denial. That is not live unpaid status and not successful paid restoration. ACC-04 needs all three states observed against the real hosted authority, and the only honest entry into the verified state is a human Restore sign-in with an already-paid account. D-10 keeps the walkthrough automated against the actual browser and limits human intervention to protected steps such as this sign-in.
Output: One Playwright spec carrying the three-state matrix, a blocking human-action checkpoint for the sign-in, and a bounded support-state record with per-row pass or blocked status.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| hosted support service → review server and browser | Live status, start, and refresh responses cross into the product and into evidence. |
| human GitHub session → Playwright ephemeral context | Real authentication material exists inside the test browser context for the duration of the Restore sign-in. |
| support state → durable evidence record | The installation id, hosted origin, and flow URL must never reach a committed record. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-20 | Spoofing | verified-state claim | mitigate | Verified status is accepted only from live hosted refresh or status responses confirmed by the read-only persisted store; the spec writes no store file, mocks no endpoint, and intercepts no support response. |
| T-07-21 | Repudiation | blocked verified row | mitigate | Deadline expiry or hosted failure produces a `blocked` row with a named reason and a `substituted` flag of false, and forces the record status to `partially-blocked`. |
| T-07-22 | Information Disclosure | hosted flow URL | mitigate | Only the equality of the opened tab's origin with the configured service origin is asserted and recorded; the full authentication URL is never captured or logged. |
| T-07-23 | Information Disclosure | installation id | mitigate | The record retains only the store status and whether a verified-at timestamp existed; the 43-character installation id is excluded and `publishScenarioRecord`'s rejection regular expression is the backstop. |
| T-07-24 | Information Disclosure | real browser profile and GitHub session | mitigate | The sign-in happens in Playwright's ephemeral context under the isolated support HOME; the fake browser-opener shim prevents the product from launching the operator's real browser; the context is discarded with the run. |
| T-07-25 | Tampering | support store | mitigate | `support.json` is opened read-only and parsed against the product's own schema; no hand edit or seeded flag is permitted. |
| T-07-26 | Denial of Service | unbounded polling | mitigate | Verification polling is bounded by an explicit deadline that resolves into a blocked row rather than hanging the suite. |
| T-07-27 | Tampering | unrelated user state | mitigate | The run uses only the isolated shared support HOME and disposable Git fixtures; the operator's real installations, caches, skills, and review data are untouched. |
| T-07-SC | Tampering | package-manager installs | accept | This plan installs nothing. |
</threat_model>
