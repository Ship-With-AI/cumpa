<decisions>
- **D-DERIVE — expectations come from the root, and that is not a tautology.** Deriving a spec's expected colour from the same root the app renders does not test the root's value; it tests that the element in question actually resolves to the token the contract says it should. A component repointed at the wrong token still fails. Whether the root's values are the *right* values is settled by 08-02's mockup-derivation check and by the visual check in Task 3. Do not "fix" this by reintroducing literals.
- **D-REBUILD — never trust the output directory.** Two suites execute a packed tarball rather than the source tree, and a stale bundle still carries the outgoing palette, so a token rename can appear to pass with no spec edited at all. Every browser run in this plan is preceded by a full build.
- **D-ROLE-CHANGES-ARE-EXPECTED — update the assertion, never the CSS.** Where a surface's radius, focus offset, or type role changed, the spec expectation moves to the new value. Do not edit `src/web/styles.css` from this plan to make an old assertion pass; 08-02 owns that file and its values were derived from the approved contract.
- **D-NO-LOCATOR-CHURN — class selectors are contractual.** Several asserted selectors override Monaco's own DOM and several match decoration class names built at `src/web/monaco/diff-semantics.ts:75,81,89`. This plan changes expected *values*, never locators. A spec reporting that a locator resolved zero elements means something upstream renamed a selector, which this phase forbade.
- **D-KEEP-GREEN-SPECS-UNTOUCHED.** Several asserted values are unchanged by the re-derivation — the canvas, panel, and default-border colours among them. Where a spec is already correct, leave it byte-unchanged and record that in the SUMMARY. Churning a passing spec to look busy removes evidence that the value genuinely did not move.
</decisions>
