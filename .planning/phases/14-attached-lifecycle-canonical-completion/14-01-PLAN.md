Create a strict optional attached marker on both existing `SessionResponseSchema` members, shaped as `attached: { kind: "agent-review" }`. It is injected only by the non-TTY launch owner. Absence preserves the current interactive DTO and route surface.

Add `AttachedCompletionStatusSchema` as the public status union `{ kind: "waiting" }`, `{ kind: "finishing", expectedRevision }`, or `{ kind: "completed", revision }`. Add strict `FinishReviewRequestSchema` containing only `expectedRevision: RevisionSchema`. Add `FinishReviewResultSchema` discriminants `completed`, `alreadyCompleted`, `revisionConflict` (expected/actual), `staleAnchors` (affected IDs/count only), `scopeInvalid`, `draftReadOnly`, `persistenceFailure`, `canonicalizationFailure`, and `deliveryFailed`. Unknown fields and malformed bodies use the existing generic 400 unavailable response; all lifecycle results are parsed before emission.

Register attached-only authenticated strict-empty-query `GET /api/review-completion` and bounded JSON `POST /api/review-completion/finish`. Map first `completed` to 201, immutable `alreadyCompleted` to 200, definitive pre-delivery revision/stale/scope/read-only refusals to 409, definitive pre-delivery persistence/canonicalization failures to 500, and terminal `deliveryFailed` to 500 before nonzero shutdown when a response remains possible. The routes do not exist for ordinary sessions, and `/api/export` never reads or changes completion state.

`AttachedCompletionCoordinator` owns session-local `waiting`, one shared in-flight `finishing` promise, immutable `completed`, and terminal-failed delivery state. `finish(expectedRevision, operation)` suppresses duplicates. A retry-safe refusal returns to Waiting only after the attempt settles and no delivery began. Once delivery begins, any rejection, partial/ambiguous write, or process failure is terminal and cannot return to Waiting or redeliver. A successful delivery freezes completed revision; the CLI separately awaits the successful response-settlement signal.

Extend `DraftStore` with the smallest queue-safe two-phase `settle(expectedRevision, { prepare, finalize })` API inside the existing private `runSerialized(queueKey, ...)` boundary. Phase 1 loads canonical bytes and prepares one frozen accepted state plus raw fingerprint/missing sentinel. A missing file is accepted only for expected revision 0 as an in-memory empty revision-0 draft and is never persisted. Phase 2, still before delivery and while the queue is held, re-reads draft presence/raw bytes and invokes `finalize(prepared)` to reobserve scope, reverify every anchor, validate the already-canonicalized prepared bytes against the accepted revision/provenance, and only then await delivery. If a missing draft appears, bytes change out of process, or any final check differs, refuse with zero delivery. Keep `runSerialized` private and add no lock.

Range preparation validates frozen `RangeReviewScope`, exact endpoints/reviewKey/pathspec order, current unchanged selector observation, and every accepted anchor through `verifyAnchor`; exact-patch preparation validates digest/validation target/reviewKey, current `PatchSnapshot` status `unchanged`, and every accepted anchor through the snapshot verifier. Build V2 or V3 and call `canonicalizeReviewExport` exactly once. Finalize repeats current scope and anchor verification, parses/checks those prepared bytes without reserialization, and delivers the unchanged bytes only when draft presence/fingerprint, scope, anchors, accepted revision, and canonical provenance still agree.
</interfaces>

<shared_outcome_contract>
This contract is identical across Plans 14-01, 14-02, and 14-03:

- **Retry-safe definitive refusal:** revision conflict; stale/unavailable anchor; invalid range or patch scope; corrupt/incomplete/read-only draft; or definitive persistence/canonicalization failure before delivery. Zero delivery is attempted. After the attempt settles the coordinator returns to `waiting`; the CLI stays attached with empty stdout; the browser shows the exact UI-SPEC recovery and may issue a later explicit Finish only after recovery. There is no automatic retry.
- **Terminal or ambiguous failure:** delivery has begun and rejects, is partial, or becomes ambiguous; stdout EPIPE; signal; server/process failure; or connection loss after Finish before confirmation. The coordinator never returns to `waiting`; browser/client code offers no same-page Finish retry and never claims success; the CLI performs one shutdown and exits nonzero. Any partial stdout bytes are not a successful canonical document and are never retried or followed by another document.
- **Completed:** canonical delivery resolves exactly once, the successful Finish response settles, then shutdown returns exit 0. Completed review state is immutable and duplicates return `alreadyCompleted`.
</shared_outcome_contract>

| Boundary | Description |
|---|---|
| Browser → loopback Fastify | Untrusted lifecycle query/body/headers cross the existing Bearer/Host/Origin boundary. |
| Fastify → coordinator | Authenticated Finish attempts a one-shot transition with distinct retry-safe and terminal outcomes. |
| Coordinator → two-phase draft settlement | Preparation/finalization races queued mutations, missing-file appearance, and external byte replacement. |
| Capability → Git/snapshot/canonical bytes | Submitted scope, anchors, and prepared bytes can become stale before delivery. |
| Capability → terminal delivery | Validated canonical bytes cross to CLI stdout; delivery may be partial or ambiguous. |
